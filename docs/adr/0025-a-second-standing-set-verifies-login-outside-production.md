# ログイン込みの画面変更は、常設のもう1組で本番より前に確かめる

ログインを要る画面が増えるほど、「本番でしか通しで確かめられない範囲」も一緒に増える（#183）。
ドメインを跨ぐと Cookie が乗らないため（ADR-0019）、Vercel の preview から直に繋いでもログインの
内側までは確かめられず、待つ理由も無くなった。**常設のもう1組を作る。**

## 決めたこと

- **画面は Vercel の preview をそのまま使う。** ブランチの割り当ても、画面を別の場所で配ることも
  しない。確かめるときだけ、preview に同じ登録可能ドメインの下の名前を alias で張る
- **もう1組の preview の `VITE_SERVER_URL` は、もう1組のサーバへ向ける。** マージ前の画面が
  本番のサーバに繋がりうる状態を、これで閉じる
- **サーバは本番と同じマシンに、常駐単位・置き場・中継の口をもう1つずつ置く。** 運び方は
  `deploy:server` が既に持っていた `--unit` / `--remote-path` で足りる（下記）
- **ログインは本番と同じ Google のクライアントを使う。** 折り返し先を1つ足すだけで、
  `packages/server/src/sign-in.ts` のコードは変えない

## 選ばなかったもの

- **preview の URL（`*.vercel.app`）から直に繋ぐ。** `vercel.app` は Public Suffix List に
  載っているので、どの preview もサーバとは別のサイトになる。`SameSite=Lax` の Cookie は
  握手に載らず、戻り先も1つしか持てない（ADR-0019）。`SameSite=None` にすれば載るが、
  どのサイトからでもその人として WebSocket を張れるようになるので採らない
- **ログインしなくても遊べるようにする（#211）を先にする。** ログインの道筋そのもの（#177）は
  何も変わらず、ログインの内側の画面（#196）も preview から繋ぐ限り Cookie が載らないので
  確かめられないままである。#183 の手当てにはならないので、#211 はそれ自体の価値で別に判断する
- **もう1組ではログインをモックにする。** 秘密を置かずに済み、何人ぶんでも入れるが、コードを
  足して「本番で開かない」ことを別に守る必要がある。まずは本物の Google で始め、アカウント2つで
  試すのが重くなったら切り替える。常駐単位や DNS はそのまま使える
- **もう1組専用の Google クライアントを作る。** Google の `sub` はクライアントをまたいで同じ
  なので、身元は分けられない。秘密が1つ増えるだけになる

## 増えるもの

常駐単位1つ、中継の口1つ、DNS2本、置き場2つ目、Vercel のドメイン1つ。**費用は増えない。**
確かめるたびの作業は、サーバを運ぶことと alias を張ることの2つ。**ホスト名・ドメイン名は
ここには書かない**（ADR-0015）。

## 誤って本番へ反映しない仕組み

`deploy:server` の既定の宛先は本番のままである。もう1組へ運ぶつもりで引数を忘れると、
マージ前のサーバで本番を差し替えてしまう。**取り違えにくい呼び方として、もう1組専用の
コマンドと環境変数を別に立てた。**

- `pnpm deploy:server` — 本番。`REVOLUTION_DEPLOY_HOST` 等を読む（今までどおり）
- `pnpm deploy:server:verify` — もう1組。`REVOLUTION_DEPLOY_HOST_VERIFY` 等、末尾に
  `_VERIFY` が付いた別の環境変数を読む

環境変数の名前そのものを分けたので、片方だけをシェルに設定していても、もう片方のコマンドには
拾われない。**引数を省いたときに、意図しない宛先へ届くことが無い。** 運び方そのもの
（束ねる・運ぶ・差し替えて立て直す）は `tools/deploy-server-core.mjs` に1箇所だけ置き、
本番用ともう1組用はそれぞれ既定値と環境変数名だけを持つ薄い入口にした。

サーバの配り忘れ（#196 の後に起きた）は、これでは防げない。もう1組へ運ぶ習慣が付くだけで、
本番へ運ぶ手順は今までどおり手で行う。

## 運ぶ人と、動かす人を分ける

もう1組の常駐単位は、本番と同じ `revolution` では走らせない。**専用の利用者
（`revolution-verify`）を、ログインの手段を持たない実行専用として作る。** SSH で運ぶのは
今までどおり `revolution` で、sudoers はユニット名を指定した行を別ファイルとして追加する
（既存の行は変更しない）。

- **運ぶ側（`revolution`）が置き場の所有者、動かす側（`revolution-verify`）はグループとして
  読むだけ。** 動かす側にはそのプロセスの中身を書き換える権限を持たせない
- **`revolution-verify` はホームディレクトリもログインシェルも持たない。** 本番の `revolution`
  はログインもプロセスの実行もできる1つの利用者だが、もう1組では両者を分けたぶん、
  実行専用の利用者が晒す面は本番より狭い

## Vercel の Environment 機能とのすり合わせ

Vercel のプロジェクト設定画面（Environments）でドメインを割り当てる際、**ブランチの指定を
求められる。** それでも `vercel alias set <preview のURL> <ドメイン>` は、割り当てられた
ブランチに関係なく、指定した preview へ張り替えられることを確かめた。**「ブランチの割り当てを
しない」という決定は崩れていない。** 画面上のブランチ指定は初期値を埋めるだけのもので、
確かめるたびの張り替えには影響しない。

## 確認できたこと

もう1組で、ログイン → ロビー → 対戦を1つ、最後まで通しで確認できた。Google のリダイレクト
先を1つ足しただけで、`packages/server/src/sign-in.ts` のコードは変えていない。

## 影響

- **ADR-0019 の「ブラウザ側の決まりは置き場に出して初めて確かめられる」は、事実上いつも本番を
  指していた。** 常設のもう1組ができたことで、同じ確認が本番より前に行えるようになった
- **ADR-0015 の「同じ形で2台目を立てることはできない」は変わらない。** あれは対戦の部屋がメモリ
  にしかなく、2人が同じプロセスに繋がっていなければ対戦が成立しないという、本番の対戦サーバに
  ついての制約である。ここで足すのはそれとは別の常駐単位で、本番の対戦とは何も共有しない
- **ログイン込みの画面変更を確かめるたびに、本番へ触れずに済むようになった。** 確かめる操作は
  サーバを運ぶことと alias を張ることの2つで、どちらも本番の常駐単位・DNS・Vercel ドメイン設定
  には触れない

# 手札の枚数はどちらのプレイヤーの分も効果が参照でき、常在型能力は BP と SP の変更を 1 つの能力で返す

決定日: 2026-11-01。開発者と決定した。

## 背景

「相手の手札が 0 枚なら、このカードの BP を＋N」「相手の手札が 0 枚なら、このカードの SP を＋N」のような常在型能力を実装したい。いまの engine では、どちらも実装できない。

- 効果が参照する盤面のビュー（`DuelView`）は、支配者自身の手札を中身ごと返す（`hand()`）が、相手の手札は枚数も返さない。エネルギーゾーンとスマッシュゾーンには、どちらのプレイヤーの分も枚数を取得するメソッド（`energyCount(player)`・`smashCount(player)`）がある。手札とその枚数の扱いは、ADR-0052 で「別の決定になる」として先送りにした。
- 常在型能力が返せる変更は、BP の変更（`BpModifier`）だけである。SP の変更（`SpModifier`）は、作成された継続効果にだけ渡せる（ADR-0036 の「ＳＰを変える常在型能力は、書くテキストが出た時に口を足す」）。

後のエキスパンションには、同じ系統のテキストがほかにもある。

- 手札の枚数を、しきい値として単発効果の条件に使う形（「相手の手札が 3 枚以上なら、相手は手札を 1 枚捨てる」）と、枚数そのものを数値として使う形（「X は相手の手札の枚数÷2 に等しい」）。
- 常在型能力の 1 文で、BP と SP を一緒に変更する形（「BP を＋X し SP を＋Y」）。ほかの味方に効果を及ぼす形（「ほかの〈属性〉の味方の SP を＋N」）。さらに、能力を与えることや移動方向を変更することまで、1 文に含む形。

## 決定事項

### 手札の枚数は、どちらのプレイヤーの分も取得できるメソッドで返す

- **`DuelView` に `handCount(player)` を追加する。** 渡したプレイヤーの手札の枚数を返す。`energyCount`・`smashCount` と同じシグネチャである。
- **返すのは枚数だけである。** 手札の枚数は公開情報で（総合ルール 第2部 第23章 1-1）、中身は非公開情報である。枚数を参照できるようになっても、相手の手札の中身を参照することも、そのカードを対象にすることもできない（ADR-0002・ADR-0004）。
- **真偽値を返すメソッド（「0 枚か」）にはしない。** しきい値の形にも、数値として使う形にも、同じメソッドで対応できるようにするためである。
- 自分の手札の枚数は、`hand().length` でも `handCount(自分)` でも参照できる。書き方は 2 通りになるが、ほかの枚数を取得するメソッドとシグネチャをそろえることを優先する。
- 常在型能力も、効果と同じ `DuelView` を受け取る（`continuous.ts` の `gather`）。このため、メソッドを追加するのはこの 1 か所でよい。

### 常在型能力は、BP と SP の変更を 1 つの能力で返す

- **BP を修整する常在型能力を、BP と SP の変更を混ぜて返せるように広げる。** 「BP を＋X し SP を＋Y」のテキストは 1 つの能力として実装し、条件と算出方法を 1 回で済ませる。
- **名前は、BP に限らない意味のものにする。** 戻り値の型は、いまは BP と SP の変更だけに絞る。能力の付与や移動方向の変更を常在型能力から返せるようにする時は、名前を変更せずに、戻り値の型を広げる。その時は、(2) テキストを変更する継続効果と (5) BP・SP を変更する継続効果とで、適用の段階が異なる（総合ルール 第4部 第12章 5-2）。engine が段階ごとに能力を呼び出し、その段階の種類だけを取得する仕組みと、段階によって参照できる盤面が異なることの扱いは、その時に決定する。
- **SP の変更も、BP の変更と同じ段階で集計する。** どちらも、属性を変更する継続効果を適用した後の盤面を参照する（同 5-2 の (5)）。そのうえで、作成された継続効果の分を足す。スマッシュで与えるダメージも、ここで集計した SP を参照する。
- 作成された継続効果に渡す値（`ContinuousModifier`）は変更しない。

## 検討した選択肢

### 手札の枚数

- **相手の分だけを返すメソッド（`opponentHandCount()`）。** 自分の枚数の書き方は `hand().length` の 1 通りで済む。しかし、ほかの枚数を取得するメソッドとシグネチャがそろわない。採用しない。

### 常在型能力の型

- **名前も型も、BP・SP のものにする（「BP・SP を修整する常在型能力」）。** 今回の範囲では、名前がもっとも正確である。しかし後のエキスパンションには、能力を与えることや移動方向を変更することまで 1 文に含む常在型能力があり、それを実装する時に、もう一度名前を変更することになる。採用しない。
- **SP を変更する常在型能力を、別の型で追加する。** 既存の型と名前を変更せずに済む。しかし、「BP を＋X し SP を＋Y」の 1 文を 2 つの能力に分けることになり、条件と算出方法を 2 回書く。テキストの上では 1 つの能力なのに、能力の並びには 2 つ含まれる。後のエキスパンションで数十枚出てくる形である。採用しない。
- **今回、能力の付与まで返せるようにする。** (2) と (5) は適用の段階が異なり、段階ごとに参照できる盤面が異なることの扱いを決定する必要がある。それは、能力を与える常在型能力を実装する時に決定することなので、今回は含めない。

## 既存の決定との関係

- **ADR-0036。** 「常在型能力の戻り値の型は `BpModifier` に絞るので、SP の変更を常在型能力が返す書き方は型で弾かれる」としていた。この決定で、常在型能力も SP の変更を返せるようになる。同 ADR の冒頭に、この 1 点を知らせる 1 行を追加する。
- **ADR-0052。** 先送りにしていた「相手の手札の枚数を、効果が読むこと」を、この ADR で決定する。手札を捨てさせる命令そのものは変更しない。
- **ADR-0002・ADR-0004。** 効果に返すのは枚数だけで、相手の手札の中身は返さない。
- **ADR-0018・ADR-0053。** 名前を変更するだけで、既存のカードの BP の変更は変化しない。SP を変更する常在型能力を持つのは、今回実装するカードだけである。このため、記録済みの対戦を打ち直した結果は変化しない。スマッシュのダメージで SP を参照する経路を BP と同じ経路に寄せることも、既存のカードでは値を変化させない。

## 影響

- `DuelView` にメソッドが 1 つ追加される。通信のデータと画面は変更しない。修整した後の SP は、すでに通信のデータに含まれ（ADR-0036 の `EffectiveUnitData.sp`）、画面にも表示されている。
- 常在型能力の型・作成する関数・プロパティの名前を変更する。既存のカード（BR1.0・トライアルデッキ・EB1.0）とテストは、名前を置き換えるだけで、動きは変化しない。
- この決定で実装できるようになるカード（EB1.0 の番号）は、004・027・052。055 と 075 は、ほかの不足（「気合」が誘発したことを参照する、支配者が相手の手札を見て選ぶ）が残る。

## 実装

- 手札の枚数: `DuelView.handCount(player)`
- 常在型能力の型: `ModifyingAbility`（旧 `BpModifyingAbility`）。`FriendshipAbility` は `ModifyingAbility` を継承する
- 作成する関数: `modifying`（旧 `bpModifying`）
- プロパティ: `modifiers`（旧 `bpModifiers`）。常在型能力のうちこの種類であることは、`'modifiers' in ability` で見分ける
- 戻り値の変更の型: `PassiveModifier = BpModifier | SpModifier`
- 盤面を参照して変更を返す関数の型: `PassiveModifiersFromBoard = (duel: DuelView) => readonly PassiveModifier[]`。`modifying` の引数と `modifiers` プロパティに使う
- カードから能力を取得する関数: `modifyingAbilitiesOf`（旧 `bpModifyingAbilitiesOf`、`card.ts`）
- 関数の型の名前で採用しなかった候補: `Modifiers`（関数だと伝わらない）、`ModifierSource`（`gather` では、source は「能力を持つユニット」の意味で使っている）、`TextModifier`（ADR-0036 の「テキストを変更する継続効果」と紛らわしい）、`ModifiersFromBoard`（作成された継続効果の解決でも盤面から値を算出するので、どちらの側かを名前から判別できない）
- `ModifyingAbility`・`modifying` に `Passive` を付けないのは、`kind: '常在型能力'` を持ち、ほかの常在型能力の型（`AttributeAddingAbility` など）と同じ付け方にするため。`modifying` は、カードを実装する側が毎回書く関数でもある

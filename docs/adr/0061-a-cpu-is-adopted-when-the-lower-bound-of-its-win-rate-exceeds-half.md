# CPU は、勝率の信頼区間の下限が 50% を上回った時に採用する

決定日: 2026-11-03。開発者と決定した（#365）。

## 背景

ADR-0060 で、CPU は段階を踏んで強くし、新しい段階の CPU は前の段階の CPU に勝ち越した時だけ採用することにした。何をもって勝ち越したと言うかは、まだ決定していなかった。

勝率は、CPU 同士にデュエルを打たせて測る（`packages/cpu` の `compareCpus`）。2 回のデュエルを 1 組にし、1 組の 2 回は同じシード・同じデッキで、CPU の席だけを入れ替えて打つ。山札の並びも先攻・後攻も同じになるので、2 回の違いは CPU だけになる。いまの CPU（合法手からランダムに選ぶ）同士では、200 回のデュエルが 1 分ほどで終わる。

## 決定事項

- **決着したデュエルの勝率の 95% 信頼区間（Wilson のスコア区間）の下限が、50% を上回れば勝ち越しとする。** デュエルの数が少ないと区間が広がるので、たまたま勝ち越しただけでは勝ち越しにならない。
- **引き分けと手数上限で打ち切ったデュエルは、勝率に入れない。** 数は別に出す。
- **既定は 200 回のデュエル（100 組）とする。** 差が小さい CPU 同士を比べる時は、デュエルの数を増やして測る（`pnpm cpu-compare` の `--duels`）。
- **1 組の 2 回を、独立な試行として扱う。** 1 組の 2 回は同じシードを使うので、独立な試行ではない。しかし、運で勝敗が決まった組は 1 勝 1 敗になり、勝率を 50% に寄せる。このため、独立として扱っても判定が甘くなることはない。

## 検討した選択肢

- **組を単位にした判定。** 1 組の 2 回をまとめて 1 つの試行とし、2 勝の組と 2 敗の組だけを比べる。試行が独立になり、統計としては正しい。しかし、1 勝 1 敗の組を除くぶん試行が減り、結果の読み方も 1 つ増える。上に書いたとおり、このままでも判定は甘くならないので、採用しない。
- **既定のデュエルの数を増やす（たとえば 1000 回）。** 小さな差も見分けられる。しかし、段階 3 以降は探索のぶん 1 回のデュエルが重くなり、比べるたびに待つ時間が長くなる。段階 2 の CPU とランダムな CPU の差は大きく、200 回で見分けられる見込みである。差が小さくなった時に、その時だけ増やせば足りる。採用しない。

## 既存の決定との関係

- **ADR-0060。** 勝ち越したと言える基準を段階 1 で決定する、とした部分の受け皿である。ADR-0060 の「実装」の節は、判定する関数の名前とこの ADR への参照だけを持つ。

## 影響

- CPU を変更するプルリクエストは、`pnpm cpu-compare` で前の CPU に勝ち越したことを示す。
- 差が小さい CPU 同士では、200 回では勝ち越しと判定されないことがある。その時はデュエルの数を増やして測り直す。

## 実装

- 判定する関数: `packages/cpu` の `verdictOf`。信頼区間は `wilsonInterval`
- 既定のデュエルの数: `tools/cpu-compare.mjs` の `--duels` の既定値 200

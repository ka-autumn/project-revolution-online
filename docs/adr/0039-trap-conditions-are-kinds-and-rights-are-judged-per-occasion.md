# トラップの発動条件は種類で持ち、発動する権利はきっかけごとに判定する

「攻撃された時」「スマッシュされた時」を発動条件にするトラップを書けるようにする。engine が持つ発動条件は侵入だけで、発動する権利は「バトルかスマッシュ判定が進行中なら発生しない」と判定している。攻撃もスマッシュも、バトルやスマッシュ判定と切り離せないできごとなので、発動条件の種類を足すだけでは足りず、権利がいつ発生するかから決め直す。

この文書は設計として先に書く。実装はこの後に行う。コード上の名前は実装の時に決め、決めた名前と読み方をそれぞれの項に書き足す。

## 呼び名

**きっかけ** — 発動条件を満たしたできごとの写し。発動した効果に渡される。「侵入してきた敵」「攻撃された味方」「スマッシュした敵」は、ここからしか取れない。侵入については既にこの形で持っている。

## 決めたこと

### 発動条件の種類

- **トリガーアイコンを、種類で分けた値として持つ。** 取りうるのは次の 3 つで、1 枚のトラップが持つのはどれか 1 つである。
  - **侵入** — 赤く塗られたスクエアの並び。いまの `triggerIcon` の中身である。
  - **攻撃** — 絞り込みを 1 つ持てる。持たなければ絞り込まない。
  - **スマッシュ** — 追加の値を持たない。
- **攻撃のアイコンの絞り込みは、アイコンの一部として、軸と値の組で持つ。** 絞り込みつきの攻撃のトラップは、印刷されたトリガーアイコンが、攻撃のアイコンと絞り込みを合わせて表している。開発者が実物で確認した読みである。画面はこの値からアイコンを描く。
  - **軸は、メーカーシンボル・色・属性の 3 つである。** いま使うカードがあるのはメーカーシンボルだけで、色と属性は、これから実装するカードのトリガーアイコンに印刷されていることを、開発者が確認した。後から軸を足すと、カードの定義・通信の表記・画面の描画の形がもう一度変わるので、最初から軸つきの値にしておく。
  - **述語にしない。** 軸が数え上げられるためである。軸が増える時は、値を 1 つ足す。
  - **1 枚のトラップが持つ絞り込みは、多くて 1 つである。** 2 つ重なるカードは無いことを、開発者が確認した。
- **効果が受け取るきっかけの型は、アイコンの種類から決まる。** 侵入のトラップは侵入のきっかけだけを、攻撃のトラップは攻撃のきっかけだけを受け取る。あらゆるきっかけを 1 つの広い型で受ける形にはしない。カードの側に、常に同じ側へ倒れる分岐が要るようになるためで、侵入だけだった時の決まり（`effect.ts` の `TrapEffect`）をそのまま 3 種類に広げる。
- **きっかけは次の 3 種類である。** どれも、できごとが起きた時点の姿を写して持つ。発動されるまでにそのユニットがスクエアを離れていれば、効果は対象を失う。
  - 侵入: 侵入してきたユニット（いまのまま）。
  - 攻撃: 攻撃したユニットと、攻撃されたユニット（総合ルール 第3部 第11章 4）。
  - スマッシュ: スマッシュしたユニット。

### 発動条件が満たされる時

- **発動条件の成立は、侵入と同じ入れ物（満たされた発動条件）に載せる。** 誘発イベントには載せない。総合ルールは、誘発イベントを誘発型能力のテキストの語句として定義し（第4部 第3章 1）、満たされると能力が自動的に誘発してバンクに入る（同 2）。トラップの《 》とトリガーアイコンは発動条件であり（第2部 第10章 3-2、第12章 2）、満たされても自動では何も起きず、発動する権利が生まれるだけである（同 第20章 3-8）。条文が分けている 2 つを、engine の中でも分けたままにする。
- **「攻撃された」は、トラップの支配者のユニットが、バトルの攻撃されたユニットになることである。** バトルが発生しなければ、満たされない（総合ルール 第3部 第11章 1-1）。第１バトルステップで、ユニットの「攻撃された時」を誘発させる所（総合ルール 第3部 第12章 1）と同じ時点で確かめる。絞り込みがあれば、攻撃されたユニットが、その軸でその値を持つ時だけ満たされる。色と属性は、継続効果を適用した後の姿で確かめる（ADR-0036）。
- **「スマッシュされた」は、相手がスマッシュの特別な行動（総合ルール 第3部 第9章 1）を、トラップの支配者に対して行ったことである。** 効果によるダメージは含めない。同条がこの行動を「スマッシュする」と名づけていることによる読みで、設計の時に前提として示したものである。
- **侵入は、置き方を問わず確かめる。** 条文は「相手のユニットが置かれること」と書き（総合ルール 第2部 第20章 3-6）、置き方を限っていない。engine は登場と移動でしか確かめておらず、効果でスクエアに置いた時（`effect.ts` の `placeOnSquare`）には、侵入も「勇気」の起動条件も確かめていなかった。これは抜けであり、直す。開発者が確認した読みである。
  - **効果で置いた時は、`resolve.ts` の `checkPlacedByEffect` が確かめる。** 命令「スクエアへ置く」を実行した後に、置かれたユニットの、置かれた瞬間の姿を写して、登場・移動と同じ 2 つの判定（`trap.ts` の `checkIntrusion`、`courage.ts` の `checkCourageCondition`）に渡す。
  - **別のスクエアにいるユニットを、効果で置き直した場合も含める。** ゾーンからスクエアへ置いた場合と同じに扱う。移動の行動が侵入になるのに、効果で動かすと侵入にならない、という食い違いを残さないためである。条文に明示の無い読みで、開発者が決めた。
  - すでに満たされている時に満たし直されても、最初のきっかけを持ち続ける、というのは単位 2 の暫定の扱いだった。単位 4 で、きっかけごとに 1 件ずつ持つ形に置き換えた（下の「単位 4 で実装で決めたこと」）。

### 発動する権利

- **権利を止めるのは、発動条件が満たされた後に発生したバトルとスマッシュ判定だけである。** 条文は「発動条件が満たされた後、優先権を得る時に『バトル』または『スマッシュ判定』が発生した場合」に権利の発生を止める（総合ルール 第2部 第20章 3-8 ただし書き、第3部 第11章 5、第17章 4）。条件より前から進行中のものは、権利を止めない。engine の「進行中ならすべて止める」という判定（`priority.ts` の `deferringRights`）を、この形に改める。ここから、次の 3 つが決まる。
  - **攻撃のトラップは、そのバトルの中で、ダメージの応酬の前に発動できる。** 権利は、第１バトルステップで優先権を得た時に発生する。実際の運用がそのとおりであることを、開発者が確認した。
    - **理由は、「攻撃された」が、バトルが発生した後に満たされると読むことによる。** そのバトルは条件より前に発生しているので、権利を止めない。トラップの「攻撃された」がいつ満たされるかを定めた条は無く、これは読みである。根拠は 3 つある。「攻撃されたユニット」は、バトルの間の呼び名である（総合ルール 第3部 第11章 4）。「攻撃された時」に誘発する能力は、第１バトルステップで扱う（同 第12章 1）。相手のユニットが自分のユニットのいるスクエアに置かれても、ほかのルールエフェクトが先に解決されて、バトルが発生しないことがある（同 第11章 1-1 と、その例）。置かれただけでは、攻撃されたことにならない。開発者が、同 1-1 の例を踏まえて確認した読みである。
    - **相手のユニットが置かれた時点で満たされる、とは読まない。** そう読むと、バトルは条件の後に発生するので、ただし書きが権利を止める。確認した運用と合わなくなり、攻撃だけの例外が要る。
  - **スマッシュのトラップは、スマッシュ判定が終わってから発動できる。** スマッシュの行動で条件が満たされ、その後、優先権を得る時にスマッシュ判定が発生するので、判定が権利を止める。ダメージが 1000 未満で判定が発生しなければ、スマッシュの行動の直後に権利が発生する。実際の運用もそのとおりであることを、開発者が確認した。
  - **バトルやスマッシュ判定の途中に、効果でユニットが置かれて侵入が起きた時は、その途中でも、次に優先権を得た時に発動できる。** 進行中のバトルや判定は、条件より前に発生しているためである。運用上の前例を確かめたわけではなく、開発者の読みである。
- **権利は、きっかけごとに判定する。** 満たされた発動条件は、きっかけごとに 1 件ずつ持つ。1 枚のトラップに複数件ありうる。これまでは、すでに満たされているトラップがもう一度満たされても、最初のきっかけを持ち続けていた。権利を失う前に 2 度満たされる場面が無かったためで、効果で置いた時の侵入と、バトル中のバトル（総合ルール 第3部 第11章 4-1）での攻撃によって、その場面が出てくる。
  - **発動する時、権利が発生しているきっかけが複数あれば、支配者が 1 つ選ぶ。** 1 つなら選択は出ない。権利が止まっているきっかけは選べない。バトル中のバトルでは、後のバトルの間に選べるのは後の攻撃のきっかけだけで、先の攻撃のきっかけは、後のバトルが終わってから選べるようになる。開発者が決めた形である。
  - **選ぶ操作は、発動の中の選択に載せる。** 行える手「トラップを発動する」の形は変えない。
  - **優先権をパスして失うのは、権利が発生しているきっかけだけである。** 止まっているきっかけは残る（総合ルール 第2部 第20章 3-8 が失わせるのは「権利を獲得した後」である）。
- **「勇気」を起動する権利にも、同じ規則を当てはめる。** 条文は、権利を止める規定を、トラップと「勇気」に同じ文で書いている（総合ルール 第3部 第11章 5、第17章 4）。判定は 2 つで共有したままにする。

### 実装で決めたこと（トリガーアイコンを種類つきの値にする単位）

- **名前**
  - `TriggerIcon` は `IntrusionIcon`（`{ kind: '侵入', squares }`）・`AttackIcon`（`{ kind: '攻撃', filter? }`）・`SmashIcon`（`{ kind: 'スマッシュ' }`）のどれかである。
  - 攻撃の絞り込み `TriggerFilter` は、軸ごとに値の型を持つ `{ axis: 'メーカーシンボル', value } | { axis: '色', value: Color } | { axis: '属性', value }` である。色の値が `Color` に限られ、軸と値の組を取り違えられない。
  - 型名は英語、値は日本語（ADR-0003）。
- **トラップは、必ずトリガーアイコンを 1 つ持つ。** `defineTrap` で省略させない。総合ルール 第2部 第20章 3-8-b の「スクエアが書かれていない」トリガーアイコンは、スクエアを持たない種類（攻撃・スマッシュ）のことで、アイコンを持たないトラップの規定ではない。侵入のアイコンで `squares` が空のものは、どのスクエアでも満たされない。
- **きっかけの型は、トラップの型をアイコンの種類で分けて決める。** `TrapCard` は `IntrusionTrapCard`・`AttackTrapCard`・`SmashTrapCard` の和で、効果の型がそれぞれ違う。
  - 侵入のトラップの効果は、今までどおり `TrapEffect`（侵入のきっかけを受け取る）である。
  - 攻撃・スマッシュのトラップの効果は `TrapEffectWithoutOccasion` で、まだきっかけを受け取らない。攻撃したユニット・スマッシュしたユニットなどは、型の上で取り出せない。それぞれのきっかけの型は、発動条件の判定と一緒に単位 5 で入れる。攻撃のトラップが侵入のきっかけを受け取る、という形を残さないための入れ物である。
  - 入れ子の `triggerIcon.kind` を見ても、カードそのものの型は絞れないので、`isIntrusionTrap` で絞る。
- **発動条件の判定は、侵入のトラップだけに行う。** 攻撃・スマッシュのトラップは、相手のユニットが置かれても発動条件が満たされず、発動する権利も発生しない（`trap.ts` の `checkIntrusion`、`play.ts` の `activateTrap`）。判定を足すのは単位 5 で、その時にこの期待を書き換える。満たされた発動条件の通信の形は、この単位では変えない（単位 4）。
- **通信の表記と、古い画面との互換。**
  - 通信の表記の `triggerIcon` は、スクエアの並びから種類つきの値に置き換える。欄は 1 つのままにし、古い形の欄を重ねて送らない。カードの定義も通信の表記も、2 つの欄の組み合わせが書けてしまう形にならない。
  - 古い画面はトリガーアイコンをスクエアの並びとして読む（`triggerIcon.length > 0`）。種類つきの値は並びでないので、落ちずにアイコンを描かない。**侵入のトラップのアイコンも、画面を読み込み直すまで出ない。** ADR-0038 の、黙って飛ばさず読めないと言う、という形とはずれるが、古い画面は読めないことを言う手段を持たないので、移行の間のこととして受け入れる。画面とサーバの版を突き合わせる仕組み（#217）が入れば、読み込み直しを促せる。
  - 新しい画面は、種類を読む分岐の最後の枝で、知らない種類（古いサーバが送るスクエアの並びも、種類を持たないのでここに落ちる）を受ける。図を描かず、読み上げに「（表示できないトリガーアイコン）」と書く（ADR-0038）。新しい画面に古いサーバがつながる間（画面だけが先に配られ、サーバがまだ古い間）は、実装済みの侵入のトラップが全部、アイコン（盤面・デッキを組む画面）と絞り込みへの当たりを失う。画面は並びを侵入として読み替えない。この期間は、ADR-0029 の配り順（マージとサーバの配り直しを同じ日に行う）で短くして受け入れる。
  - 互換は、古い画面の読み方を写し取ったテストで確かめる（`wire.test.ts`）。
- **見た目。** 攻撃とスマッシュは、印刷されたアイコンをなぞる。絞り込みは枠の左下に文字で書き、メーカーシンボルと属性は値のまま、色は英語で書く。トリガーアイコンは、印刷と同じく、テキストの側の左に置く。詳しくは ADR-0027 に書き、モックも直した。
- **デッキを組む画面のカードの絞り込み。** 発動条件に「攻撃された時」「スマッシュされた時」を足し、トリガーアイコンの種類で振り分ける（ADR-0028）。
- **非公開側の実装済みの侵入のトラップ。** 書き方だけを移した。スクエアの並びを作るヘルパーは `intrusionIcon` に改め、侵入の値を返す。図の文字列は変えていない。移す前と後で、トラップ全部のスクエアが同じことを確かめた。

### 単位 4 で実装で決めたこと（権利をきっかけごとに判定する単位）

- **「条件が満たされた後に発生した」ことの判定。** 満たされた発動条件と起動条件は、満たされた時の `DuelState.log` の長さを `metAt` として持つ。バトルとスマッシュ判定は、始まった時のログの長さ（`Battle.startedAt`・`SmashJudgment.startedAt`）を、すでに前後の比較（外側と内側の決定）に使っている。`startedAt` が `metAt` 以上の手順が 1 つでも進行中なら、その件の権利は止まっている（`priority.ts` の `deferringRights`）。手順が始まる時は必ずその見出しがログに積まれるので、先に始まっていた手順は `metAt` より小さく、条件が満たされた直後に始まった手順は `metAt` 以上になる。
  - バトル中のバトルでは、後のバトルが終わると、先のバトルの中でまた権利が発生する。バトルとスマッシュ判定が始まる所・終わる所には手を入れていない。
  - フェイズの行動を止める判定（`activePlayerMayAct`、ADR-0012）とは共有しない。あちらは進行中のものをすべて見る。
- **きっかけごとに持つ。** 満たされるたびに 1 件ずつ足す（`checkIntrusion`・`checkCourageCondition`）。1 枚のトラップに何件でも並ぶ。「勇気」の起動条件も同じで、置かれたユニットの写し・その時エネルギーの条件を満たしていた「勇気」・`metAt` を 1 件として持つ。起動しても件は消えない（総合ルール 第5部 第2章 3）。
  - パスで失うのは、権利が発生している件だけである（`loseTrapRightOnPass`・`loseCourageRightOnPass`）。
  - 権利を持つ側の効果がユニットを置いてバトルを起こした場合、そのバトルは条件の後に始まるので権利が止まり、パスしても失わない。バトルが条件より前から進行中なら、権利は止まっていないので、パスで失う。
- **選択。** 権利が発生している件が 2 件以上ある時だけ、発動（`activateTrap`）・起動（`activateCourage`）の最初に、支配者に選ばせる。1 件なら出さない。止まっている件は候補に並ばない。目的は `'トラップのきっかけ'`・`'勇気のきっかけ'`（`resolve.ts` の `CHOICE_PURPOSES`）で、`source` に発動するトラップ・起動する「勇気」を載せる。行える手「トラップを発動する」の形は変えない。
  - 候補の形は `{ kind: 'きっかけ', occasion }`（`protocol.ts` の `WireCandidate`）。`occasion` の種類は、トラップが `{ kind: '侵入', invader: { card, square } }`、「勇気」が `{ kind: '置かれた', unit: { card, square } }`。「勇気」の起動条件はトリガーアイコンと関係が無く（総合ルール 第5部 第2章 2）、用語「侵入」（CONTEXT.md）とは呼べないので、種類を分けた。できごとの写しなので、いまの盤面のカードではなく、置かれたユニットの識別子とスクエアで指す。発動までにスクエアを離れていても、同じユニットが 2 度置かれていても、並べられる。種類は、単位 5 で攻撃・スマッシュが足される。
  - 画面は、番号のボタンに、トラップなら「侵入 〈ユニット名〉（〈スクエアの呼び名〉）」、「勇気」なら「置かれた 〈ユニット名〉（〈スクエアの呼び名〉）」と書く。盤面のカードを押す形にはしない。問いの文は「〈トラップ名〉を発動するきっかけを選んでください」「〈カード名〉でダメージを与えるユニットを選んでください」。モックは `?trap-occasions` で見られる。
- **通信の形と、古い画面との互換。**
  - 満たされた発動条件の通信の形（`WireTrapConditionMet`）は変えない。1 枚のトラップの件が複数並んでよい。`metAt` は権利の判定にだけ使うので、通信に載せない（`wire.ts` の `toWire` が落とす）。相手のぶんを丸ごと落とす隠し方も、いまのままである。
  - 古い画面が新しいサーバにつながる間は、画面が満たされた発動条件を読んでいないので、件が増えても変わらない。きっかけの選択は、知らない目的・知らない形の候補（ADR-0038、#285）として、「選んでください」と番号だけのボタンで出る。落ちずに答えられるが、何を選んでいるかは読めない。移行の間のこととして受け入れる。
  - 新しい画面が古いサーバにつながる間は、古いサーバがきっかけの選択も 2 件目の件も送らないので、いまと同じに動く。ただし、バトルやスマッシュ判定の途中に置かれた侵入では、サーバが古いうちは発動できない。ADR-0029 の配り順で短くして受け入れる。
  - 古い画面の側の互換は、新しい目的と候補の形が、古い画面にとっては知らない値の枝（#285）に落ちることに頼っている。基準点の `input-model.ts` の `candidateLabel`・`askingFor` は、知らない形・知らない目的を番号だけの表示に落とす。この枝そのものは、実物のコードを通す既存のテスト（`input-model.test.ts` の「この画面が知らない種類なら、目的を言わない文になる」と「この画面が知らない形の候補」）が確かめている。古い画面の読み方を写したテストは置かない。写しは実物のコードを通らないので、古い画面から枝が消えても通ってしまい、何も守らない。古いサーバの形（1 枚 1 件）を新しい画面が受けて、表示が変わらないことは `view-model.test.ts` で確かめる。
- **効果が受け取るきっかけの型は変えない。** 侵入のトラップの効果は `TrapEffect`（侵入のきっかけ）のままである。攻撃・スマッシュのきっかけの型は、発動条件の判定と一緒に単位 5 で入れる。
- **テストで確かめた場面。** Issue の「テストで確かめる場面」のうち、第２バトルステップ以降に権利が持ち越されないことと、割り込んだバトルの間は権利が止まり、パスでも失わず、終わった後に発生することは、侵入に置き換えて、この単位で確かめた（`trap-rights.test.ts`）。攻撃のトラップの形で書き直すことと、バトルが発生しなければ攻撃の発動条件が満たされないこと（総合ルール 第3部 第11章 1-1）は、攻撃の判定を足す単位 5 で確かめる。

## 検討した選択肢

**攻撃・スマッシュの成立を誘発イベントに載せる** — 「何かが起きた時」の入口が 1 つになる。しかし、誘発の先はバンクで、トラップはバンクに入らない。誘発イベントから別の入れ物へ分ける分岐が要り、満たされた発動条件の入れ物も結局残る。ユニットの「攻撃された時」は、攻撃されたユニット自身の能力だけを見る作りで、トラップゾーンのカードへ広げると意味が変わる。

**スクエアの並びの欄は残し、攻撃・スマッシュの欄を別に足す** — 既存の侵入のトラップと通信の表記が変わらない。しかし、「スクエアの並びが空で、別の欄がある」「両方ある」という組み合わせが書けてしまい、きっかけの型を決めるにも 2 つの欄を合わせて見ることになる。

**攻撃のアイコンに、メーカーシンボルだけを持てる欄を置く** — いま使うカードには足りる。しかし、色や属性で絞り込むカードが来た時に、欄の形を変えることになり、通信の表記の形の変更をもう一度行うことになる。

**発動条件を述語（関数）で書く** — どんな絞り込みでも書ける。しかし、関数は通信に載らず、画面がアイコンを描けない。書ける形が広がりすぎる。

**進行中のバトルとスマッシュ判定はすべて権利を止め、攻撃だけを例外にする** — いまの判定に例外を 1 つ足すだけで済む。しかし、規則が原則と例外の 2 段になり、条文が書いていない場面を止める側へ倒す読みになる。

**2 度満たされた時に、最初のきっかけを持ち続ける／新しいきっかけで上書きする** — 盤面と通信の形が変わらない。しかし、どちらも、もう一方のきっかけに対して発動したい場面に応えられない。実際の卓では、どのできごとに対して発動するかを、発動する人が決める。

## 既存の決定との関係

- **ADR-0012 と食い違う箇所がある。** 同 ADR の「影響」は、トラップの発動と「勇気」の起動について、「進行中に行えないのは権利がそもそも発生しないため」「条件がたまたま同じなので、判定そのものは 1 つ置いて共有する」と書いている。この決定の後は、進行中でも権利が発生することがあり、フェイズの行動を止める判定とは条件が同じでなくなる。フェイズの行動を止める決定そのもの（同 ADR の本体）は変えない。実装の時に、同 ADR の該当の項へ、「権利の判定はこの文書に移った。フェイズの行動を止める判定とは共有しない」と書き足す。
- **ADR-0010 は変えない。** 発動できるかどうかは、これまでどおり、サーバが送る行える手に現れる。画面は判定を持たない。
- **既存の「勇気」を持つカードの動きが、1 つの場面でだけ変わる。** 効果でユニットが置かれた時に起動条件が満たされるようになり、それがバトルやスマッシュ判定の途中なら、その途中で起動できる。登場と移動で条件が満たされる場面は、バトルや判定の途中には起こらない（ADR-0012）ので、変わらない。
- **既存の侵入のトラップは、書き方だけが変わる。** トリガーアイコンの欄が種類つきの値になるためで、挙動は変えない。

## この決定が決めていないこと

- **満たされた発動条件の、古い画面との互換。** トリガーアイコンの表記の互換は「実装で決めたこと」に、きっかけごとに持つ形にした時の互換は「単位 4 で実装で決めたこと」に書いた。
- **「スマッシュされた時」を誘発イベントにも足すか。** そこで誘発する能力を持つカードが無いので、足さない。出てきた時に決める。
- **「同じイベントで起動条件を満たした勇気を起動すると、トラップを発動する権利を失う」（総合ルール 第2部 第20章 3-8）の扱い。** engine はまだ実装していない（#22）。「同じイベント」の単位をどう取るかは、そちらで決める。この決定の後は、トラップの権利も「勇気」の権利も、ユニットが置かれたできごとごとに持つので、単位を決める時の手がかりになる。
- **絞り込みが 2 つ重なるカードと、侵入・スマッシュのアイコンの絞り込み。** どちらも、そうしたカードは無い。出てきた時に、値の持ち方を決め直す。
- **スマッシュした敵が、発動までにスクエアを離れていた時の、個々のカードの読み。** きっかけは写しで渡すので、効果の側が、いまもスクエアにいるかを確かめて決める。

## 影響

- **トリガーアイコンを読んでいる所がすべて変わる。** engine の侵入の判定、通信の表記、画面の盤面・デッキを組む画面・カードの絞り込み、モック、実装済みの侵入のトラップの定義である。
- **満たされた発動条件の入れ物が、1 枚のトラップにつき複数件を持てる形になる。** 権利・喪失・相手への隠し方・通信の形が、きっかけごとになる。
- **バトルとスマッシュ判定の途中で、トラップの発動と「勇気」の起動が起こるようになる。** その効果がさらにバトルやスマッシュ判定を発生させることがある。
- **サーバを配り直す時は、進行中の対戦が無いのを確かめる。** サーバは立て直すと、進行中の対戦を記録した行動と答えから打ち直す（ADR-0018）。権利の判定をきっかけごとに改めたので、改める前に記録された対戦を打ち直すと、結果が変わりうる。条件より前から進行中のバトルの間にパスして権利を失い、その後に記録された「トラップを発動する」が行えなくなる。件が 2 件以上になり、コストの答えがきっかけの選択に使われる。打ち直しの例外を `replay`・`restore` は受け止めていないので、起これば、配り直し直後の復元が例外で落ちるおそれがある。この危険は以前からあるが、この変更はそれが表に出る場面を持つ。当面は運用で避ける。例外を部屋ごとに受け止める修正は、別の Issue で扱う。
- **条文に明示が無い読みを含むので、テストの根拠にはこの ADR を併記する**（ADR-0006）。
- **この決定で書けるようになる形（BR1.0 の番号）。** 攻撃のトラップ（58）、絞り込みつきの攻撃のトラップ（55。効果の側は、ADR-0036 の作成された継続効果と ADR-0035 のメーカーシンボルを使う）。スマッシュのトラップ（59）は、発動条件ときっかけまでがこの決定で、効果の側は ADR-0042 が要る。

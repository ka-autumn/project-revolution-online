# 身元は Google から受け取り、席は Cookie のセッションで決まる

身元を Google のログインから受け取る。**サーバが預かるのは Google 上の識別子 1 つと、本人が付けた表示名だけである。** 繋ぐときの名乗り（`?participant=`）は Cookie のセッションに置き換え、**ADR-0009 の「名乗り＝席に座れる合言葉」をここで畳む。**

何をどこに保存するかは決まっている（ADR-0018）。**その上に、誰であるかを載せる。**

## 秘密は自分で持たず、外に預ける

誰でも使える想定で進める（#177）。**固定の口で出し続けている以上、「知っている人が繋げる」という性質はすでに外に出ている**（ADR-0014）。そこを閉じる。

**自分で持つと、忘れたときの再発行にメールを送る手立てが要る。** そこで外部のサービスが 1 つ増える。**外に預けても増えるのは 1 つで、そちらは秘密も再発行も持たなくてよい。** 増える数が同じなら、持たないほうを選ぶ。

**預ける先は Google 1 つにする。** 増やすほど、作る量よりも運用（登録・鍵の管理・落ちたときの切り分け）が増える。**後から足せる**——識別子を `(発行元, sub)` の組で持っておけば、2 つ目を足したときに既存の行が壊れない。

**引き換えに、Google が落ちれば新しく入れない。** これは ADR-0013 と ADR-0014 が避けてきた「外に依存を作る」判断と逆を行く。**入っている人は続けられる**（セッションを持つのはこちらである）ので、止まるのは入口だけである。それを承知で選ぶ。

## 預かるもの、預からないもの

- **預かる** — 発行元と `sub`（Google 上の識別子）、本人が付けた表示名、セッション
- **預からない** — メールアドレス、本名、写真

**求める scope は `openid` だけにする。** 表示名を本人に付けさせるので、`profile` も `email` も要らない。**これは設定ではなく決定である。** ADR-0018 は「置き場に残るものは公開できないものとして扱う」と書いた。**その重さを、預かる中身を減らすことで最小にする。** 置き場が失われたときに漏れるものが、識別子と自分で付けた名前だけになる。

**そのぶん、Google のアカウントを失った人を助ける手立ては無い。** メールアドレスを持たないとはそういうことである。持てば助けられるが、持てば守るものが増える。**ここでは持たないほうを選ぶ。**

## 依存は増やさない

- **ID トークンの署名を自前で検証しない。** Google の token endpoint から TLS で直に受け取るので、経路がそのまま出所の証明になる。**JWT を読むライブラリが要らない。** 受け取った中身のうち、`aud` が自分の client_id であることだけは確かめる
- `fetch` は Node に入っている

**実行時依存は `ws` のままである。** ADR-0001 が見ているのはエンジンで、ここはサーバの話だが、**足さないという性質はサーバでも守れる。**

## 繋ぐときの名乗りは Cookie にする

**出発点は、ブラウザの `WebSocket` にヘッダーを足す口が無いことである。** 渡せるのは URL と protocols だけで、`Authorization` を載せる場所が無い。

| 手 | 載る場所 | 繋ぎ直し（ADR-0016）への影響 |
| --- | --- | --- |
| **Cookie** | **握手の HTTP リクエスト** | **無し。ブラウザが自動で載せる** |
| `Sec-WebSocket-Protocol` に混ぜる | ヘッダー | 無し。ただしプロトコル名を名乗る欄の流用 |
| 使い捨ての入場券を URL に | URL（短命・1 回限り） | **繋ぎ直すたびに取り直しが要る** |
| 寿命つきのトークンを URL に | URL | 無し。**中継のログに残ったものが寿命の間ずっと使える** |

**Cookie にする。** URL に何も残らず、`HttpOnly` にすれば画面の JS からも読めない。そして**繋ぎ直すところに手を入れなくてよい。**

最後の点が効く。`connection.ts` は切れてから 10 回まで、待ちを倍々に伸ばしながら自分で繋ぎ直す（ADR-0016）。**入場券にすると、その 10 回それぞれの前に HTTP を 1 往復挟むことになる。** 諦めるまでのおよそ 30 秒がその往復に食われ、**入場券を出す口が落ちていれば、WebSocket は張れるのに繋ぎ直せないという壊れ方が増える。**

**手元で確かめた。** HTTP と WebSocket を同じポートに同居させ、握手のときに `request.headers.cookie` が読めることを見ている（`ws` 8.21）。**ブラウザが実際に送るかどうかは、置き場に出してからでないと通しで確かめられない**（次節）。

### Cookie に `Domain` を付けない

画面は Vercel、サーバは常駐マシンで、出所が違う（ADR-0013、ADR-0015）。**いまのブラウザは、出所が別の登録可能ドメインだと Cookie を送らない。** したがって、**画面とサーバを同じ登録可能ドメインの下に置く**（`app.example.com` と `duel.example.com` のように）。同じドメインの下なら、出所が違っても送られる。

**`Domain` 属性は付けない。** 付けると、画面を配っている側にもセッションが送られる。**配り先に預ける理由が無い。** 属性を付けなければ、Cookie はサーバのホストにだけ送られ、そこには握手も含まれる。

**ADR-0013 の「画面とサーバは同じ出所である必要が無い」は、ここで半分だけ畳まれる。** 繋ぐことについては今も要らない。**身元を持つなら、同じドメインの下が要る。**

**ドメインを揃えられないことになった場合は、使い捨ての入場券に落とす。** 上の表のとおり繋ぎ直しに費用がかかるが、動かないよりはよい。**先に作らない。**

### 折り返しの戻り先は、サーバの設定に持つ

Google から戻ってきたところで、画面へ送り返す。**その戻り先を URL で受け取らない。** 受け取ると、どこへでも人を送れる口をこちらで開くことになる。設定に持ち、そこへしか戻さない。

**行きと帰りが同じ人のものであることは `state` で確かめる。** 短命の Cookie に置いて突き合わせる。

## ログインしているかどうかを、画面は判断しない

画面は `HttpOnly` の Cookie を読めない。**読めなくてよい。** 繋ぎに行き、サーバが「ログインしていない」と返したらログインへ送る。

**何を行えるかを決めるのはサーバである**（ADR-0010）。ログインしているかどうかも同じ軸に乗る。画面に判断を持たせると、**サーバが断るのと画面が出すものが食い違ったときに、どちらが正しいかを決める場所が無くなる。**

## 手元で立てるときは、名乗りのままにする

**Google の設定が無いときだけ、`?participant=` で入れる。設定があるときは受け付けない。両方であることはできない。**

手元で 2 人ぶん試すのも、テストを回すのも、これで今までどおり動く（README の書き方も残る）。**置き場は必ず設定を持つので、そこではこの口は閉じている。** 「開発用の抜け道を、うっかり本番で開けたままにする」形にしないために、**開いているかどうかを別の旗で持たない。**

## ここでは決めないこと

部屋と席を身元に紐づけ直すところ（#177 の 3 段目。ロビーに名前を出すのもそこ）、表示名の決まり（重複を許すか、変えられるか、使えない文字）、ログアウトと退会の口、迷惑対策。

## 影響

- **対戦サーバが HTTP も喋るようになる。** いまは WebSocket を受けるだけの口である——ADR-0013 が「サーバは WebSocket を受けるだけの口で、そこに挟む場所が無い」と書いたのは、この形のことだった。**その前提が変わる。** 中継の設定も、WebSocket を通すだけでなく通常の HTTP の道を足すことになる（ADR-0015）
- **置き場に秘密が 1 つ増える**（Google の client secret）。**リポジトリに書かず、環境変数で受け取る。束ねたものにも焼き込まない。** ADR-0015 が宛先について決めたのと同じ形である
- **ADR-0009 の「誰であるかは繋ぐ時の URL で名乗る」を畳む。** 名乗りは手元で立てたときだけのものになる
- **ADR-0013 の「同じ出所である必要が無い」を、身元については畳む。** 同じ登録可能ドメインの下に置く
- **セッションは ADR-0018 の置き場に入る。** 行を消せばその場で切れるので、ログアウトも締め出しも同じ 1 つの手立てになる
- **Google が落ちれば新しく入れない。** 入っている人は続けられる
- **ブラウザが実際に Cookie を送ることは、置いてから目で確かめる。** 手元で確かめられたのは、HTTP と WebSocket が同じポートに同居できることと、握手で Cookie が読めることまでである。**ブラウザの側の決まり（`SameSite` と、同じ登録可能ドメインであること）は、置き場に出して初めて通しで確かめられる。** 確かめる前に 3 段目へ進むと、動かない理由が 2 つ重なる

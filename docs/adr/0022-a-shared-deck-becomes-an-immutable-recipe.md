# 共有したデッキは、手を離れた不変のレシピになる

組んだデッキを人に渡せるようにする。**共有すると、そのときの中身を写し取った不変のレシピができる。** ゲームの中ではコピーして自分のデッキにでき、`/recipe/<鍵>` を開けばレシピの画面（共有を全部並べる）から読める——**開けるのはログインしている人だけである。** **共有した人が渡すリンクは `/share/<鍵>`。** 共有 1 つだけの公開ページで、**ログインしていなくても開ける。**

デッキそのものは ADR-0021 にある。ここで決めるのは、それが持ち主の手を離れるところである。

## デッキとレシピは別のものである

**デッキは持ち主のもので、直せる。レシピは写し取ったもので、変わらない。**

共有を「自分のデッキに見せる旗を立てること」にすると、**デッキを直した瞬間、渡した相手が見ているものが変わる。** 外へ出た URL は取り消せないので、「使ってみて」と渡したものが翌日には別のデッキになっている。**渡したものが変わらないことは、渡す行為の前提である。**

**写し取ったものが変わらないだけで、カードの姿までは焼き付けない**（ADR-0021）。カードの実装が直れば、レシピの見え方も直る。**不変なのは「何が何枚か」であって、カードそのものではない。**

## 決めたこと

### 何が起きるか

- **共有すると、中身を写し取ったレシピが 1 つできる。** 元のデッキを直しても、配ったものは変わらない。
- **同じ中身のレシピは 1 つに決まる。** デッキは保存するときに並びが揃うので（ADR-0021）、中身から鍵を決められる。**同じものが二重に並ばない。**
- **レシピと共有は別のものとして持つ。** 共有は「ある人が、あるレシピを、ある名前・解説・公開の段階で出したこと」で、**レシピ 1 つに共有がいくつもぶら下がる。** ただし、共有はいつも増えるとは限らない——**同じ人が同じレシピをもう一度共有すると、行は増えず、その人の既存の共有が書き換わる**（名前・解説・公開の段階・確かめた形式とリスト・共有した時刻）。同じ人の同じレシピへの行が何行も並ばないようにするためである。行が増えるのは、別の人が共有した時と、自分がいったん取り消してから共有し直した時である。
- **共有する時、名前（40 文字）と解説（1000 文字）を書く。初期値はそのデッキの名前と解説で、書式は持たない。** デッキの名前・解説と同じ上限を使う（`server` の `owned-deck.ts`）——共有してから人の目に触れるものだからといって、上限を別に持つ理由が無い。
- **共有する人が、形式と禁止／制限リストを選んで規定を確かめる。** 選び方は部屋を作る時と同じで、満たしていなければ理由を添えて断る（判定はサーバ側、ADR-0010）。**確かめるだけで、選んだ形式とリストは共有ごとに残す。レシピ本体には持たせない**——ADR-0021 が「デッキはどのルールで組んだかを持たない」と決めたのと同じ理由で、レシピに焼き付けると、リストが変わった時に全部の共有が古い判定を抱えることになる。
- **共有には 2 段階あり、共有ごとに持つ。「リンクを知っている人だけ」と「一覧に載せる」。** 身内に渡すつもりのものが新着に流れることを、取り消しではなく設定で防ぐ。**あとから変えられる。**
- **共有した後にリストが変わって規定を満たさなくなっても、何もしない。** レシピはそのまま残り、断られるのは席に着く時である（ADR-0021 の「規定を満たしているかは、残すときと席に着くときの両方で確かめる」と同じ考え方）。
- **共有は取り消せる。取り消せるのは自分の共有だけである。** 共有が 1 つも残っていない（全部取り消された）レシピは開けない。ほかの人の共有が残っている間は開ける。**すでにコピーした人の手元のデッキは、その人のものなので残る。** 取り消したあと、同じ中身を誰かが共有すると共有が 1 つ増えてまた開けるようになるが、**取り消した共有そのものは取り消されたまま残り、その人の名前で復活しない。**
- **コピーできるのは 3 つ。** 開発者が置いた既製デッキ、人が共有した共有（レシピではなく共有を指す——名前と解説はコピーした共有のものが付く）、**対戦が終わった相手のデッキ**（ADR-0021）。どれも同じ操作で自分のデッキになり、コピー後は元と独立している。
- **レシピの画面は、共有を全部並べる（共有者・名前・解説、新着順）。** 同じ中身に複数の人の読みが並びうる。**共有ごとにコピーできる。**
- **共有した人が渡すリンクは、共有ごとに分かれる（`/share/<鍵>`）。** 同じレシピに複数の共有がぶら下がりうる（前項）ので、渡した相手には渡した本人の名前・解説だけが届く。**`/recipe/<鍵>`（レシピの画面、共有を全部並べる）とは別の鍵を、共有 1 つごとに持つ**（`ShareId` とも別——`ShareId` は認証済みの接続の上でしか使わない値で、公開の URL には乗せない）。

### 一覧

- **載るのは、「一覧に載せる」共有が 1 つ以上あるレシピである。**
- **新着順と、コピーされた数の多い順を切り替えられる。** 「新着」はそのレシピの一番新しい「一覧に載せる」共有の時刻で、**コピー数はレシピ単位で数える**——どの共有からコピーされたかは数えない。
- **一覧に出すのは、一番新しい「一覧に載せる」共有の名前と解説である。**
- **同じレシピをもう一度共有すると、その人の共有そのものが書き換わる**（「何が起きるか」を見よ）ので、**公開の段階も一緒に変わる。** 「一覧に載せる」で共有していた人が、同じレシピを「リンクを知っている人だけ」で共有し直すと、その共有は非公開になり一覧から消える——**そのレシピに他人の「一覧に載せる」共有が残っていなければ、レシピごと一覧から落ちる。** 共有し直すことは自分の共有を編集することであり、「共有の公開範囲を変える」で同じ変更をした場合と結果が揃う。身内向けに戻したいなら、共有し直すか、公開の段階を変えればよい。
- **絞り込み（カード・色）は作らない。** 範囲外とする。

### 外で何が見えるか

`/recipe/<鍵>`（レシピの画面）を開けるのはログインしている人だけである。未ログインには中身を一切出さず、ログインへ促す。**`/share/<鍵>`（共有 1 つの公開ページ）だけが、この線を緩める。**

- **ログインしていない人には、カード名・枚数・色・レベル・種別と、共有者が書いた解説まで出す。** 大会のデッキリストと同じ形で、レシピとして十分に通用する。種別（ユニット・ストラテジー・トラップ・超必殺ストラテジー！）ごとに枠を分けて出す。
- **能力テキストと、その他の表記（属性・スター・ムーブアイコン等）は、ログインした人にだけ出す。** レシピが数本たまれば、テキストまで出す口はカード事典の公開になる。ADR-0002 が避けているのはそれである。カードの表記はカードプールを引いて出す（`server` の `deck.ts` の `poolFacesOf`、ADR-0010）ので、レシピの画面のために新しい出し方は作らない。
- **興味を持った人には、入ってくるという道がある。** 共有の目的は「使ってみて」と渡せることなので、渡された人がもっと知りたくなったらログインすればよい。`/share/<鍵>` にはログインへの誘いを添える。
- **未ログインに開く口は、識別子からカード名・枚数・色・レベル・種別までである。** 総当たりすれば一覧は抜ける。**それは許容する**——出てよいと決めた以上、出る量を数える意味が無い。**テキストとその他の表記を返さない線だけを、その口で守る。**
- **共有者を出す。名前は見るたびに引き直す。** 表示名はもともと人に見せるためのもので、本人が決めている（ADR-0020）。名前を変えれば、過去のレシピの表示も変わる。**共有した時点の名前を焼き付けるのは、そのための仕組みを作ってからにする。**

### 誰が出すか

- **ユーザが直接開くのは画面の側である。** `/recipe/<鍵>` も `/share/<鍵>` も画面（クライアント）のパスで、静的に配られている画面がまず受け止める（`client` の `main.ts`）。**対戦サーバを直接開かせるのではない。**
- **`/recipe/<鍵>`（レシピの画面）は、対戦サーバがレシピの中身を返す口を出す。** 画面はすでに繋いでいる WebSocket（ADR-0009）の上でレシピを尋ね、サーバがそのレシピと、ぶら下がる共有を返す（`server` の `recipe.ts`）。開けるのはログインしている人だけなので、いまある認証済みの口に同じメッセージの形（ADR-0008）で乗せれば足りる。レシピ自体は同じマシンの置き場にある（ADR-0018）ので、新しい常駐物も増えない。
- **`/share/<鍵>`（共有 1 つの公開ページ）は、対戦サーバの新しい公開 HTTP の口が答える。** ログインの折り返しと同じポートに同居する（`server` の `serve.ts`）。**ログインしていなくても答える**——Cookie を見てログインしているかを見分け、能力テキストとその他の表記を足すかどうかを決めるだけである（`PublicShare.authenticated`）。
  - **画面と対戦サーバは別の場所に置かれる**（ADR-0013）ので、画面からの `fetch` はクロスオリジンになる。Cookie を送るには CORS で出所を許す必要があり、`*` は使えない——**出所は、戻り先の設定（`SignInConfig.returnTo`）から作る**（`sign-in.ts` の `allowedOrigin`）。向き先をもう 1 つ設定に持たない。
  - **JSON を返す。HTML は返さない。** 画面（静的に配られている SPA）がまず受け止めて `fetch` する形を崩さない——対戦サーバが直接 HTML を返す形にはしない。
  - **ログインした人には「コピーする」を出す。押すまでは WebSocket を張らない。** 繋いだ接続に対して対戦サーバは必ず 3 つのことをする——カードプール全部を送る（`sendPool`）、デッキを 1 つも持たない人に既製デッキを配る（`sendOwnDecks`）、表示名が無ければ尋ねてほかを全部はねる（ADR-0020）。ページを開いただけで繋ぐと、見るだけで満足する人全員がこれを引き受けることになる。押した時だけ繋げば、引き受けるのはコピーする意思がある人だけになる。コピーは `デッキをコピーする`（`origin: 共有レシピ`）を送り、返事（保存できた・名前が要る・行えなかった）を出したら閉じる——1 回きりの接続で、部屋には入らない。
- **レシピ・共有から読めるものを作るところと、それを返すところを分ける。** 決まりごとと I/O を分けるのは `room.ts` と `serve.ts` が既にやっていることで、ここでも同じにする（`recipe.ts` と `serve.ts`）。
- **いまは対戦サーバが答え、いずれ静的に書き出すこともありうる。** `/recipe/<鍵>` はログインしている人にしか答えない以上、静的な書き出しへ移す時は認証をどこで挟むかも一緒に決める必要がある。`/share/<鍵>` は認証を要らない前提で作ってあるので、書き出しへ移す時の壁は低い。公開のアクセスが常駐 1 台に来ることが重くなったら、そのとき測る。

## ここでは決めないこと

- **共有した時点の作者名を焼き付ける仕組み。** 名前を変えても外のページが変わらないほうがよい場面はあるが、**それは別に作るものである。**
- **静的な書き出しへ移す時期。** 移せる形にしておくことだけを決めた。
- **一覧を速くするための索引。** `shares` に `visibility` / `revoked_at` の索引を持たず、`recipe_copies` も毎回数え直す（`store.ts` の `publicRecipesOf`）。共有が増えるほど一覧の仕事は線形に増える見込みだが、カードプールの配り方（ADR-0021）と同じく、**大きくなってから測る。**

## 影響

- **対戦サーバに、ログインしていない人が来るようになった。SNS に貼られればクローラも来る。** それまで公開の口に来るのは、ログインの折り返しだけだった。`/share/<鍵>` がその線を緩めた唯一の口である。
- **`/recipe/<鍵>` への負荷は増えない。** レシピを尋ねる口は、ログインしている人にしか答えない——対戦の口に来ていたのと同じ、認証された接続の上に乗るだけである。
- **表示名が、初めてゲームの外に、そしてログインしていない人にも出る。** これまで名前が見えるのは部屋にいる相手だけだった（ADR-0020、#186）。`/recipe/<鍵>` では見えるのがログインしている人にだけだったが、**`/share/<鍵>` では未ログインにも共有者の表示名が出る**（「外で何が見えるか」）。**本名である必要がないことは変わらない**（ADR-0020）が、見える範囲がさらに広がった。
- **取り消しても、塞がらない穴が 1 つ残る。** 共有していないデッキも、対戦すれば相手に見えてコピーされる（ADR-0021）。**塞がない。** 当たったデッキを覚えて手で組み直すことは誰にでもできるので、塞いでも意味が薄い。
- **ADR-0002 が守っている線を、書き直すことになった。** 「公開リポジトリに置かない」と「誰にも見せない」は違う、というところを、あちらに書き足してある。
- **置き場に、持ち主が消しても残るものができる。** コピーされたデッキは別の人のものである。**元のレシピを取り消しても、コピーは残る。**

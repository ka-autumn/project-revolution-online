# 画面のモックをリポジトリで管理し、見た目の決まりの見本として使う

各画面の見た目（ADR-0027〜0031）は、HTML で作ったモック（実際には動かない見本の画面）を見比べながら決めてきた。ところが、そのモックはリポジトリの外に置いたままで、バージョン管理されていなかった。そのため、次の問題があった。

- モックと実装のどちらに合わせるべきかが決まっておらず、両者が食い違ったときに判断できなかった（#255 はその一例）。
- 新しい画面やダイアログを作るたびに、管理されないモックが増えていった。
- 見た目を大きく変えると、変える前の姿がどこにも残らなかった。

そこで、採用したモックをリポジトリに入れ、ADR との関係をはっきりさせる（Issue #259）。

## 決めたこと

### 決まりは ADR に書き、モックはそれを目で見て確かめるための見本とする

**見た目の決まりは、ADR に文章で書いたものが正しい。** モックは、配置や大きさ、色の組み合わせなど、文章だけでは伝わりにくいところを目で見て確かめるための見本として置く。

- ADR とモックが食い違っていたら、ADR に合わせてモックを直す。
- ADR に書かれていない細かいところは、モックを手本にしてよい。ただし、その点で迷うことが出てきたら（実装と食い違ったときなど）、決めたことを ADR に書き足す。
- 実装とモックが食い違っていたら、どちらに合わせるかを開発者が決める。実装に合わせるならモックを直し、モックに合わせるなら実装を直す Issue を作る。

### 見た目を変えるときは、モックも同じ変更で直す

**実装の見た目を変えるときは（モックと違う見た目にするときも含めて）、同じ変更の中で、その画面のモックも直す。** 決まりそのものが変わるなら、ADR も同じ変更で直す。変更を分けてしまうと、その間にモックと実装がまた食い違い、どちらが正しいかを決めた意味がなくなるからである。

新しい画面やダイアログのモックも、採用が決まったらここに置く。検討の途中で作った案は、リポジトリの外で試し、ここには入れない。

### 置き場所と分け方

`docs/mocks/` の下に画面ごとのディレクトリを作り、それぞれに `index.html` を 1 つ置く。これまでのモックは 1 つのファイルに複数の画面が入っていたが、利用者から見て別の画面になるものは分ける。

| モック | 画面 | ADR |
| --- | --- | --- |
| `duel/` | 対戦画面 | ADR-0027 |
| `duel-dialogs/` | 対戦中の確認ダイアログ・選ぶダイアログ | ADR-0031 |
| `deck-list/` | デッキ一覧 | ADR-0028 |
| `deck-builder/` | デッキ構築 | ADR-0028 |
| `lobby/` | ロビー | ADR-0029 |
| `naming/` | 名前を決める画面 | ADR-0030 |
| `waiting/` | 相手を待っている間の画面 | ADR-0030 |

- いくつかの画面で使う部品（カードの見た目の CSS、見本のカード、レベルやスターのアイコン、2 つの画面で使う CSS と JS）は、`docs/mocks/shared/` に 1 つだけ置く。同じものを複数の場所に持つと、片方だけ直し忘れることがあるためである。
- 1 つの画面の中で見た目が変わる場面（名前を決める画面で名前を断られたとき、対戦画面で勝敗が決まったときなど）は、ファイルを分けず、モックの中の切り替え（本番の画面には無い部分）で見られるようにする。
- **実装で別の画面へ移るボタンは、モックでも押すと移った先のモックが開くようにする。** 移った先は、その画面の最初の状態で開く（前の画面で選んだものは引き継がない）。ボタンを押さずに移る場合（相手が来ると、待っている間の画面から対戦画面へ移る）は、モックの中の切り替えにリンクを置く。

### 公開されているリポジトリだけで開けるようにする

モックは、公開されているリポジトリだけを clone した状態でも、ブラウザでファイルを直接開けば見られるようにする（`file://` で開ける）。

- `private/` の中のものは読まない。カードのデータも、ここに置いた見本だけを使う。
- サーバを立てずに開けるよう、`fetch` や ES モジュールは使わない（`file://` で開くと読み込めないため）。CSS・画像・ふつうの `<script src>` だけで作る。
- モックは、アプリのコード・テスト・ビルドとは切り離しておく。

### カードは架空の見本にする

モックにも、実際のカードの名前・能力テキスト・作品名は載せない（ADR-0002）。架空のカードに置き換える。

- **架空のカードの名前は「見本・」で始める。** 実際のカードと取り違えないようにするためである。
- 種類・レベル・色・スター・BP・SP・ムーブアイコン・トリガーアイコンは、実際のカードと同じくらいのばらつきを持たせる（長い名前や長い能力テキストも混ぜる）。レイアウトが崩れないかを確かめるのに使うためである。
- 能力テキストは自分で書いた文にする。「夢」「希望」のようなキーワード能力の名前は、総合ルールに出てくる言葉なので使ってよい（ADR-0007）。ただし、その説明文は自分で書いた文にする。
- 属性・作品名・ブロック（出版社）・エキスパンションも架空のものにする。出版社のロゴは使わない。
- **実際のカードでモックを見られる仕組みは作らない。** 作ると、実際のカードのデータを公開リポジトリに入れる道ができてしまうためである。
- モックを追加したり直したりするときは、コミットする前に、実際のカードの名前・作品名・属性などでモックの置き場所を検索し、1 件も見つからないことを確かめる。公開リポジトリに push したものは取り消せない。

## やらないこと

- Storybook のような、モックの代わりになる仕組みを入れること。
- スクリーンショットを置くこと。必要になったらモックから撮り直せる。
- 実装に合わせる以外の理由で、モックの見た目や作りを手直しすること（見た目を変えるなら、それは ADR とモックを一緒に直す変更になる）。

## 影響

- ADR-0027〜0031 から、それぞれのモックを開けるようにする。
- `AGENTS.md` の規約に、見た目を変えるときはモックも直すことを書き足す。
- モックの開き方や、見本のカードの作り方は `docs/mocks/README.md` に書く。
- モックを入れる時点で、モックと実装の違いを洗い出した。モックに合わせると決めた違いは Issue にした（#255・#260・#261 と、画面だけでは作れない機能の Issue）。実装に合わせると決めた違いは、モックを直した。

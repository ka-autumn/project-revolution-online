# ロビーのお知らせは、Vercel Blob に置いたファイル 1 つを画面が取りに行く

ロビーの右の列のお知らせは、見た目と窓の動き、1 件の項目（種別・版・日付・題・要約・本文・「変わったこと」の箇条書き）が ADR-0029 で決まっている。今の見た目の仕様は `docs/screens/lobby/spec.md` にある（ADR-0044）。この文書を書いた時点（2026-10-17）では、枠だけを置いて「お知らせはまだありません」を出しており、中身をどこに置き、どう画面に届けるかが決まっていなかった。

置き場を選ぶ前提として、この時点の経路は次のとおりだった。

- **画面は、公開リポジトリだけで Vercel がビルドする。** `private/` は見えない。画面と一緒に配る中身には、非公開の側にしか置けないものを入れられない。
- **Vercel が画面を配り直すのは、`packages/client`・`packages/engine` などが変わった時だけである**（`vercel.json` の `ignoreCommand`）。それ以外の場所に置いたファイルを変えても、画面は配り直されない。
- **対戦サーバは手で配る**（ADR-0015）。非公開のパッケージ（`private/decks`）はサーバのバンドルに焼き込まれる。配り直す前には、進行中の対戦が無いことを開発者が確かめている。

## 決めたこと

### 中身は非公開リポジトリに書き、公開リポジトリにも GitHub のリリースにも置かない

**お知らせには、カード名を書くことがある**（新しく入ったカードを知らせる時など）。ADR-0002 が守っているのは、リポジトリが機械可読な塊として丸ごと複製されることである。公開リポジトリのファイル・コミット・GitHub のリリースは、どれもその塊の側に入る。そこで、お知らせの元の文章は非公開リポジトリに書く。

画面に 1 件ずつ出すことは、ADR-0002 の線の内側である（カード名は画面にも、共有されたデッキのレシピにも出ている）。

**能力テキストも、書いてよい。ただし、エラッタや処理の直しの説明に要る、変わったカードの分だけにする。** エラッタは全文が無いと伝わりにくく、処理の直しもテキストを引かないと説明しにくい場面がある。

ADR-0022 は、能力テキストをログインした人にだけ出すと決めている。お知らせの置き場は、ログインしなくても読める公開のファイルなので、その線をお知らせについてだけ緩めることになる。ADR-0022 が避けたのは、レシピが溜まるとテキストまで出す口がカード事典になることだった。お知らせに出るのは、開発者が説明に要るものとして選んだ数枚である。どのカードでも引ける口にはならない。カードを並べて紹介するためにテキストを書くことは、この範囲に入らない。

### お知らせを足す・直すために、対戦サーバも画面も配り直さない

**置き場は Vercel Blob の公開ファイル 1 つ（JSON）である。** 非公開リポジトリの元の文章を、コマンドで丸ごと上げて差し替える。本番と検証で、置き場（Blob のストア）を分ける。

**画面は、ロビーを出す時にそれを取りに行く。** 開いているロビーには、その場では出さない。次にロビーを開いた時、または読み込み直した時に出る。お知らせは急ぎの連絡ではなく、リリースノートの類なので、開き直した時に出れば役目を果たす。

対戦サーバと通信の形には手を入れない。お知らせは画面と Vercel の間で閉じる。そのため、画面とサーバが別々に配られることで起きる食い違い（新しい画面に古いサーバ、など）は、お知らせには起きない。

### 既読・未読は扱わない。識別子だけを持たせておく

ロビーに未読の印は出さない。**ただし、1 件ずつに変わらない識別子を持たせる。** 端末に「どこまで見たか」を覚える形なら、後から画面だけで足せるようにしておくためである。

### 種別は「更新」「修正」「お知らせ」の 3 つのままにする

ADR-0029 が「ひとまず」としていた 3 つを、そのまま使う。振り分けは次のとおりである。

| 書くもの | 種別 |
| --- | --- |
| カードの追加・機能の追加・見た目の変更 | 更新 |
| 不具合の直し・ルールの処理の直し | 修正 |
| メンテナンスの予告・ご案内・そのほか | お知らせ |

カードの追加だけを探したい時は、1 件の中の「変わったこと」の箇条書きで読む。

### 上げる手順

1. **開発者が、非公開リポジトリのお知らせのファイルに足すか直して、コミットする。**
2. **公開リポジトリのコマンドが、ファイルの形を確かめてから、本番の置き場へ丸ごと上げる。** 確かめるのは、項目がそろっていること、種別が今の画面の読めるものであること、識別子が重なっていないこと。確かめに通らなければ上げない。ファイルのパスは引数で受け取る（`deploy:server` の `--decks` と同じく、公開リポジトリが非公開の側を名指ししないため）。
3. **検証へは、見たいときだけ上げる。** 毎回は通さない。上げ直せば直る操作なので、本番で見え方がおかしければ、直して上げ直す。

書き込み用のトークンは、本番用と検証用を別の環境変数で持つ（配布用の鍵と同じ分け方。README の表に足す）。

### 取りに行けない・読めない時は、ロビーを落とさない

- **丸ごと読めない時は、「お知らせはまだありません」を出す。** 取りに行けない時（通信の失敗、Vercel の利用枠を超えて止まった時を含む）、置き場が無い時（手元の開発など）、JSON として読めない時、形が違う時がこれに当たる。スマートフォンの縦向きでは、まだ無い時と同じく畳まずに出す（ADR-0034）。
- **1 件だけ読めない時は、その 1 件だけを外し、読める分を並べる。** 種別だけが知らないものは、札を出さずに並べ、絞り込みでは「すべて」にだけ出す。題や日付など、欠けると並べられない項目が欠けたものは外す。知らない項目は無視する。
- **種別や項目を足す時は、読める画面を先に配ってから、新しい形のお知らせを上げる。** 読めない 1 件が出るのは、開いたままの古いタブだけになる。開き直せば直る。

対戦の画面は、知らない種類を黙って飛ばさず「読めなかった」と言う（ADR-0038）。お知らせがこれと違う扱いになるのは、ADR-0038 の理由（盤面が動いたのに画面に何も出ないと、何が起きたかを追えない）が当てはまらないためである。お知らせは 1 件が欠けても、ほかの件の読み方は変わらない。

## 検討した選択肢

### 中身をどこに書くか

- **公開リポジトリの中のファイル、または GitHub のリリース** — 書くのは最も軽く、画面と一緒に配ることもできる。しかし、カード名を書けない。また、公開リポジトリの中のファイルは、置く場所によっては画面の配り直しのきっかけにならない。
- **カード名は書かず、数と種類だけで書く** — 公開の置き場が使えるようになる。しかし、新しく入ったカードを名前で知らせられないのは、お知らせの役目を欠く。

### 非公開の中身を、どこからどう届けるか

- **`private/decks` に足して、対戦サーバに焼き込む** — 新しい仕組みはほぼ要らない。しかし、お知らせを足す・直すたびに、サーバを配り直すことになる（進行中の対戦の確認を含む）。
- **対戦サーバの置き場（SQLite）に書き込む道具を作る** — 開いている画面にもその場で送れる。しかし、置き場の表・追加・修正・削除の操作・書き込みに気づく仕組みが要る。非公開リポジトリの元の文章と、置き場の中身がずれていく。
- **サーバのマシン上に置いたファイルを、対戦サーバが読み直す** — 開いている画面にも送れ、元の文章は非公開リポジトリに残る。しかし、サーバに読み直しの仕組みと、通信の形の追加が要る。その場で届ける必要は無いと決めたので、それに見合わない。
- **Vercel Edge Config（Global Config）** — 同じドメインの口になり、反映も速い。しかし、Hobby のプランでは、ストアが 1 つ・書き換えが月 100〜250 回・容量が 8 KB〜1 MB と、この時点の Vercel の文書の間で数字が食い違っていた。本文を持たせる置き場としては不確かだった。

### 既読・未読

- **端末に覚える** — ログインしなくても効く。しかし、未読の札などの見た目が ADR-0029 の外に増える。初めて来た人の扱いも決める必要がある。識別子を持たせておけば、後から画面だけで足せるので見送った。
- **サーバに覚える** — 端末をまたいで揃う。しかし、サーバに手を入れないと決めたことと食い違い、ログインしない人には効かない。

### 種別

- **「カード追加」を分けて 4 つにする** — 絞り込みが効く。しかし、タブが増えて見た目の仕様が動き、スマートフォンの幅も確かめ直すことになる。
- **「更新」と「お知らせ」の 2 つに減らす** — 書く時に迷わない。しかし、不具合の直しだけを追えなくなる。

### 上げる手順

- **毎回、検証へ上げて見てから本番へ上げる** — 本番には確かめた見た目のものしか出ない。しかし、手間が倍になり、続きにくい。上げ直せば直る操作なので、そこまで要らない。
- **1 回のコマンドで検証と本番の両方へ上げる** — 2 つの置き場がいつも揃う。しかし、先に見る役に立たない。

### 1 件だけ読めない時

- **「（表示できないお知らせ）」の行を出す（ADR-0038 に揃える）** — 扱いが揃う。しかし、押しても窓に出すものが無い行が並ぶ。
- **1 件でも読めなければ、全体を「まだありません」にする** — 最も単純である。しかし、1 件足しただけで、古い画面からお知らせが全部消える。

### 能力テキスト

- **能力テキストは、ログインした人にだけ届ける** — お知らせの本文は公開の置き場に置き、テキストだけを対戦サーバのログインした接続の上で届ける。ADR-0022 の線は守れる。しかし、対戦サーバに手を入れないと決めたことと食い違い、仕組みが 2 系統になる。Vercel の側では、ログインしているかを見分けられない（ログインは対戦サーバが持っている）。
- **能力テキストは書かず、変わったところを言葉で説明する** — 線も置き場もそのままで済む。しかし、エラッタは全文が無いと伝わりにくい。

## この決定が決めていないこと

実装の時に決める。どれも、ここで決めた置き場・届け方・手順を動かさずに選べる。

- **ファイルの項目名と、識別子の付け方。** 1 件の項目は ADR-0029 のとおりで、それに識別子を足す。「版」に何を書くか（画面の版か、お知らせの通し番号か）も、ここで決める。
- **非公開リポジトリの中の、ファイルの置き場所。**
- **画面に置き場の URL をどう渡すか、同じドメインに見せるか、キャッシュをどれだけ持たせるか。** Vercel の環境変数は Production と Preview で分けられるので、本番と検証の置き場はそれで分けられる見込みである。検証環境は preview に別名を張ったものなので、ほかの preview も検証の置き場を読む。
- **既読・未読を足すかどうか。** 公開した後に、お知らせの件数と、スマートフォンで見落とされていないかを見て決め直す。

## 影響

- **お知らせを出すのに、配り直しは要らない。** 非公開リポジトリにコミットして、コマンドを 1 回打てば、60 秒ほどで次に開いた人のロビーに出る。
- **新しいカードを足した時は、サーバの配り直しとお知らせの公開が別の手順になる。** お知らせを先に上げると、まだ遊べないカードを知らせることになるので、サーバを配った後に上げる。
- **Vercel の上で、新しく持つものが増える。** Blob のストア 2 つ（本番と検証）と、書き込み用のトークン 2 つである。Hobby のプランで利用枠を超えると、30 日間読めなくなる。その間、ロビーは「お知らせはまだありません」に戻る。
- **ログインしない人にも、能力テキストが届く口が 1 つ増える。** 何を書くかは開発者が選ぶ。範囲（説明に要る、変わったカードの分だけ）を守るのは運用である。
- **公開リポジトリだけを clone した人の手元では、お知らせは出ない。** 置き場が無いので「まだありません」になる。
- 見た目の仕様（ADR-0029・`docs/screens/lobby/spec.md`）と食い違う決定は無い。種別を「ひとまず」の 3 つで確定したことだけが、仕様書の書き方に効く（画面のプルリクエストで「ひとまず」を外す）。

## 実装

実装で決めた名前と形。上の決定は動かさない。

### ファイルの形

非公開リポジトリの中の置き場所は `private/notices/notices.json`。パッケージにはせず、`package.json` は置かない。公開側のコードはこのパスを名指ししない（コマンドは `--notices` で受け取る）。

いちばん外はオブジェクト `{ "notices": [ ... ] }`。1 件の項目は次のとおり。項目名は英語、種別の値は日本語（ADR-0003）。知らない項目は、件の中でもファイル全体でも無視する。

| 項目 | 必須 | 中身 |
| --- | --- | --- |
| `id` | 必須 | 英小文字・数字・ハイフン（`^[a-z0-9]+(-[a-z0-9]+)*$`）。書き手が付け、ファイルの中で重ならない。日付から始めるのは慣習で、強制しない |
| `kind` | 必須 | `更新`・`修正`・`お知らせ` のどれか |
| `version` | 省略可 | 空でない文字列。書き手が自由に書く。画面の版でも通し番号でもよい。無ければ画面は版を出さない |
| `date` | 必須 | 実在する日付の `YYYY-MM-DD` |
| `title` | 必須 | 空でない文字列 |
| `summary` | 必須 | 空でない文字列（平文） |
| `body` | 必須 | 1 要素以上の配列。要素は空でない文字列（平文の段落 1 つ）か `{ "quote": 空でない文字列 }`（引用の段落。能力テキストを引く時に使う） |
| `changes` | 省略可 | 空でない文字列の配列（平文。箇条書きの 1 行が 1 要素） |

「空でない文字列」は、前後の空白（全角を含む）を除いて空になるものも空とみなす。空白を含む文字列は、書き換えずにそのまま上げる。

並びは、ファイルに新しい順（上が新しい）で書く。日付は上から順に同じか古くなっていること。同じ日の前後はファイルの順が正で、画面は並べ替えない。

### 形を確かめるところ

パッケージは `@revolution/notices`（`packages/notices`、実行時依存ゼロ）。`readNotices` が 1 件ずつ検査して「読めた件」と「外した件とその理由」を返し、画面は読めた件だけを使う。丸ごと読めない時（JSON でない・外側がオブジェクトでない・`notices` が配列でない）は、それと分かる結果を返す。知らない種別の件は外さず、`kind` が `null` の読めた件として返す。`id` の重なり・日付の並び・知らない種別の拒否は `checkNoticeFile` にあり、上げるコマンドだけが使う。

### 置き場とコマンド

置き場のパス名は本番・検証とも `notices.json` に固定し、上げ直しても URL は変わらない。キャッシュは 60 秒（`cacheControlMaxAge`）。

- `pnpm publish:notices --notices <パス>`（本番）と `pnpm publish:notices:verify --notices <パス>`（検証）。`--check` を付けると形を確かめるだけで、トークンを読まず、通信しない
- トークンは環境変数だけから読む。本番は `REVOLUTION_NOTICES_TOKEN`、検証は `REVOLUTION_NOTICES_TOKEN_VERIFY` で、それぞれ相手の変数は読まない。`BLOB_READ_WRITE_TOKEN` も読まない。引数で渡す口は無い
- 形が通らなければ、理由を出して上げない。トークンは出力に出さず、`@vercel/blob` が投げた例外の文言もそのまま出さない
- 上げるのに失敗した時は、失敗の種類（アクセス拒否・ストアが無い・ストアが止まっている・送信の中断など）が分かる文言を出す。入口が例外を `instanceof` で種類の名前に直して本体に渡し、日本語への読み替えは本体にある。種類が分からない例外は、クラスの名前だけを添える
- `--notices=<パス>` のような `=` でつなぐ形は受け付けない（値を出力に出さないため）。先頭の BOM は断る。BOM を外して上げることはしない

### 丸ごとの差し替えになる理由

パス名 1 つにファイル全体を 1 回の要求で送る。成功すれば新しい中身、失敗すれば古い中身のままで、半分だけ新しい状態は無い。CDN のキャッシュにより、最大 60 秒ほど古い中身が見えることはある。

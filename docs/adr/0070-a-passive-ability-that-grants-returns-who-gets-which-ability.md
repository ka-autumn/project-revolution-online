# 能力を与える常在型能力は、与える先と能力の並びを返す

**ADR-0073 で、与えられたキーワード能力の見せ方を決定した（ここでの「画面は変更しない」のうち、プランのカードのアイコンとカードの詳細の表示が変更された。通信のデータの形式は変更しない）。**

決定日: 2026-11-11。開発者と決定した（#335）。

この文書は設計として先に書いた。実装した後で、実装で決定した名前を末尾の「実装」の節に追記する。

## 背景

EB1.0 の 026 は、自分のプランゾーンにある特定の属性のユニットに、「夢」を与え続ける常在型能力を持つ
（架空の例: 「あなたのプランゾーンにある『機械』のユニットに『夢（プランゾーンからプレイできる）』という能力を与える」）。

能力を与える効果は、作成された継続効果としてだけ実装できる（ADR-0036）。与えられる能力の種類は型で絞っていて、
今は「夢」だけである。与えられた能力は、1 つの集計（`continuous.ts` の `grantedAbilitiesOn`）を通して、
スクエアのユニットのデータ（`continuousData`）と、スクエアの外のカードのデータ（`appliedCard`）に含まれる。
プランゾーンからプレイできるかの判定も、画面へ送るプランゾーンのカードのキーワード能力も、このデータを参照している。

後のエキスパンションには、期限を持たずに能力を与える行が 53 行ある。約 25 行は EB1.0 の 026 と同じく、
プランゾーンのカードへ「夢」を与える。残りは、スクエアの味方・手札・捨札のカードへ、ほかのキーワード能力や
テキストの能力を与える。

## 決定事項

- **能力を与える常在型能力を、新しい種類として追加する。** 発生源のユニットと、効果に見せる盤面のビュー
  （`DuelView`）を受け取り、「どのカードに、どの能力を与えるか」の並びを返す。ＢＰ・ＳＰを変更する常在型能力
  （ADR-0056）と同じ形である。与える値には、作成された継続効果が使っている、能力を与える値（`granting`）を
  そのまま使う。
- **与える先は、効果から見えるカードである。** 今のビューで指せるのは、スクエアのユニットと、支配者の
  プランゾーン・手札・捨札のカードである。EB1.0 の 026 は、支配者のプランゾーンのカードを取得し、属性で絞って返す。
- **与えられる能力の種類は、今の型のままにする。** 今は「夢」だけである。種類を広げるのは別の決定で、広げた分は、
  この常在型能力からも与えられるようになる。
- **与えられた能力の集計に、常在型能力の分を追加する。** 集計が 1 か所なので、プランゾーンからプレイできるかの判定、
  画面へ送るキーワード能力、効果からの問い合わせは、今の経路のまま、常在型能力が与えた「夢」を含むようになる。
- **発生するのは、発生源のユニットがスクエアにいる間だけである**（総合ルール 第4部 第4章 1、同 第12章 4-1）。
  発生源がスクエアを離れると、次に参照した時には与えられていない。盤面には何も残さず、参照するたびに集計し直す。
  ＢＰ・ＳＰを変更する常在型能力と同じである。プランゾーンに置かれるカードは、置かれた時点で能力を与えられている
  （同 第12章 2）。
- **能力を与える常在型能力に見せる盤面は、能力を与える効果を適用する前のものにする。** 属性は、継続効果が
  追加した分を含めない。属性の変更は、テキストの変更より後に適用するためである（総合ルール 第4部 第12章 5-2）。
- **能力を与える効果どうしの順番は、今は実装しない。** 同じ種類の継続効果は、依存していない効果を先に、あとは
  発生した順に適用する（同 5-4・5-5）。今は、与えられる能力が「夢」だけで、「夢」を持つかを与える条件にする
  テキストが無い。能力を与える効果はすべて互いに独立していて、どの順に適用しても結果は同じである。
- **ログには何も積まない。** 常在型能力による継続効果は、できごとではない。ＢＰ・ＳＰを変更する常在型能力も、
  ログに積んでいない。
- **画面は変更しない。** プランゾーンのカードが、書かれた能力と違うキーワード能力を持つ時は、今でも、2 人の画面に
  そのアイコンが表示される（ADR-0036）。通信のデータの形式、仕様書、モックも変更しない。
- **CPU が「プランゾーンのカードをプレイできるか」を見積もっている所を、与えられた能力を含むデータに切り替える。**
  今は、カードに書かれた「夢」だけを参照している（`scored-cpu.ts` の、プランを残すかの判定）。切り替えないと、
  CPU は、与えられた「夢」でプレイできるプランを、プレイできないものとして捨ててしまう。作成された継続効果が
  与えた「夢」（BR1.0 の 51）についても、同じ見積もりのずれが今ある。この切り替えで、両方が直る。

## 検討した選択肢

**「自分のプランゾーンのカードへ『夢』を与える」専用の種類にする** — カードの側は絞り込みの条件だけを返せばよく、
最も小さい。約 25 行はこれで足りる。しかし、スクエアの味方へ与える形が出た時に、別の種類をもう 1 つ作成することになる。
採用しない。

**発生源がスクエアに置かれた時に、期限を持たない作成された継続効果として盤面に持つ** — 今の集計を変更せずに済む。
しかし、プランゾーンのカードが入れ替わるたびに、与え直しと取り除きを行う処理が要る。常在型能力の継続効果は、
発生した時点で影響を受けなかったカードにも影響を与える（総合ルール 第4部 第12章 4-2）ので、その時点の盤面から
決まるものとして扱う。採用しない。

**engine が、このテキストをキーワードのように知る** — 今回は最も短く実装できる。しかし、絞り込みの条件は
カードごとに違い、カードの読み方を engine が持つことになる。採用しない。

**能力を与える効果どうしの順番（依存と発生した順）を、今回実装する** — 総合ルールのとおりになる。しかし、
依存が起きるテキストの組み合わせが今は無く、確認できる場面が無い。発生した順を参照するための盤面の状態も
先に増やすことになる。採用しない。

## 既存の決定との関係

- **ADR-0036。** 与えられた能力をデータに含める仕組みと、与えられる能力を型で絞る決定は、そのまま使う。
  集計の元が 1 つ増える。
- **ADR-0056。** 常在型能力が値の並びを返す形にそろえた。
- **ADR-0018・ADR-0053。** 既存のカードはこの能力を持たないので、既存のカードの動きも、記録済みの対戦を
  打ち直した結果も変化しない。与えられた能力は盤面から一意に決まるので、打ち直しても同じ盤面になる。
- **ADR-0060・ADR-0062。** CPU の合法手は engine が作成するので、与えられた「夢」でのプレイは、合法手に含まれる。
  CPU が自分で見積もっている所だけを切り替える。

## この決定が決定していないこと

- **「夢」以外の能力を与えること。** 与えられる能力の種類を広げる決定で扱う。
- **能力を与える効果どうしが依存する時の順番の実装。** 与える条件に使われているキーワード能力を、別の効果が
  与えられるようになった時に、総合ルール 第4部 第12章 5-3〜5-5 のとおりに実装する。発生した順を参照するために、
  常在型能力を持つカードがスクエアに置かれた時点を、盤面が持つ必要がある。
- **手札のカードへ能力を与えた時の見え方。** 相手の手札は非公開情報で、与えられた能力をどう表示するかが関わる。
  そのテキストを実装する時に決定する。
- **CPU が、能力を与える常在型能力を持つカードをプレイする価値を見積もること。** 今回は見積もらず、ＢＰ・ＳＰの
  分だけで判断する。

## 影響

- 常在型能力の種類が 1 つ増える。与えられた能力の集計が、常在型能力の分を含むようになる。
- CPU の、プランを残すかの判定が、与えられた能力を含むデータを参照するようになる。
- この決定で実装できるようになるカード（EB1.0 の番号）: 026。後のエキスパンションの、プランゾーンのカードへ
  「夢」を与える約 25 行も、同じ種類で実装できる見込み。

## 実装

- 能力の型と実装する関数: `AbilityGrantingAbility`（`abilitiesGranted: (duel) => readonly GrantModifier[]`）と `abilityGranting`。カードの側から取り出す関数は `abilityGrantingAbilitiesOf`（`card.ts`）。与える値は、`granting(card, dream)` が作成する `GrantModifier` をそのまま使う。
- 集計: `grantedAbilitiesOn`（`continuous.ts`）が、作成された継続効果の分に続けて、スクエアにいるユニットの能力を与える常在型能力の分を追加する。常在型能力に見せる `DuelView` は、データを加工しない `UnitData`（`(_id, card) => card`）で作成する。集計の結果を通したビューを見せると、集計が自分自身を呼んで止まらなくなるため。
- 能力を集計する関数 `gather` は、該当する能力を持つユニットにだけ `DuelView` を作成する形に変更した。`appliedCard` はカード 1 枚ごとに呼ばれて集計し直すため、能力を持たないユニットまで `DuelView` を作成すると、呼ばれる回数に比例して重くなる。結果は変化しない。
- CPU: `scored-cpu.ts` のプランを残すかの判定は、視点の `effectiveKeywords`（書かれた能力と違うカードの分だけ含まれる）を先に参照し、含まれていなければ書かれた能力を参照する。
- CPU の空回しのビュー（`probe.ts`）の `hasKeyword` は、スクエアのユニットに与えられた能力を参照できない。視点が持つ継続効果を適用した後のデータ（`effective`）は、ＢＰ・ＳＰ・属性だけで能力を含まないため。含めると通信のデータの形式が変更されるので、この決定では直さなかった。スクエアのユニットに能力を与える実カードを実装する時に、視点のデータと一緒に直す。

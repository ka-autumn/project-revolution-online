# CPU は自分の視点だけを見て打ち、段階を踏んで強くする

決定日: 2026-11-03。開発者と決定した（#364）。

## 背景

CPU（`server` の `cpu.ts`）は、合法手からランダムに手を選ぶ。元はルールエンジンの検証用のランダム自己対戦（ADR-0005）のために作ったものを、仮の対戦相手に流用している（#175、ADR-0017）。選ばない手として除くのは、トラップ以外のカードをトラップゾーンに置く手、伏せたトラップを捨てる手、味方エリアが空いているのに中央エリアへ出す手だけである。エネルギーが 7 枚になるまでは、エネルギーを置く手だけを候補にする。

対戦相手としては、とても弱い。

- `優先権を放棄する` が、ほかの手と同じ確率で選ばれる。メインフェイズに出せるカードがあってもターンを終え、スマッシュフェイズにスマッシュしないまま進む。
- 選択への答え（`pickCpuAnswer`）も均等なランダムである。ダメージを自分のユニットに与える、強化を相手のユニットに掛ける、などが起こる。
- バトルの勝ち負け、敵エリアでスマッシュすると＋500 になること（総合ルール 第3部 第9章 1）、スマッシュの枚数（同 第3部 第3章 1）を考慮しない。

いまの CPU は盤面（`DuelState`）をそのまま受け取っている。盤面には、相手の手札、お互いの山札の並び、これから先のシャッフルを決める乱数列（`DuelState.random`）が入っている。どれも非公開情報である（総合ルール 第2部 第23章 2-1）。ランダムに選ぶだけなら何も読まないので問題にならなかったが、先読みをする CPU がこれを読むと、人には分からないことを知って打つことになる。

## 決定事項

### 段階を踏んで強くし、段階ごとに勝率で確かめる

次の順に強くする。段階ごとに実装の Issue を起票する。

1. **CPU 同士の勝率を測る仕組み。** CPU 同士を、複数のシードで先攻・後攻を入れ替えて対戦させ、勝率を出す。
2. **場面ごとに手へ点数を付けて選ぶ（ヒューリスティック）。** スマッシュを逃さない、パスしすぎない、勝てるバトルだけをする、エネルギーに置くカードを選ぶ、選択に効果の損得で答える。効果の損得は `Effect` のデータから判定し、カードを名指ししない（ADR-0002）。
3. **評価関数で盤面を採点し、自分のターンの手の並びをビームサーチで選ぶ。**
4. **評価関数の重みを、CPU 同士の勝率を測る仕組みで調整する。**
5. **見えない情報を埋めた仮の盤面で探索する（決定化モンテカルロ木探索）。**

- **新しい段階の CPU は、前の段階の CPU に勝ち越した時だけ採用する。** 勝ち越したと言える対戦の数と勝率は、段階 1 の Issue で決める。
- CPU は 1 つだけ置く。難易度は、強い CPU ができてから考える。

### CPU は自分の視点の盤面だけを見る

- **CPU の手を選ぶ関数と、選択に答える関数は、CPU の席から見た射影の盤面（`perspectiveOf`）だけを受け取る。** 盤面（`DuelState`）を受け取る形にしない。人の画面が受け取るものと同じ範囲の情報で打つ（ADR-0004）。見てはいけないものを渡さないことを、型で守る。
- **先読みに使う盤面は、射影の盤面の見えない部分を埋めて作った仮の盤面に限る。** 本物の盤面から先読みしない。乱数列も、仮の盤面のために引き直す。
- **自分のデッキの中身は知っていてよい。** 人も自分のデッキは知っている。並びは知らない。

### 見えない情報の補い方は、推定の元を差し替えられるようにする

- **相手のデッキリストは知らない前提にする。** 対戦で使っている相手のデッキを、推定に使わない。
- **見えないカードは、推定の元（ありうるデッキやカードの集まり）から埋める。** 推定の元は差し替えられる形にする。初めは、その対戦で使えるカードの全体を元にする。後で、成績上位者のデッキリストなどを元にして、推定の範囲を調整できるようにする。
- この決定が関わるのは、仮の盤面を作る段階（3 以降）からである。推定の元の形は、その段階の Issue で決める。

### 検証用のランダム自己対戦と、対戦相手の CPU を分ける

- **検証用のランダム自己対戦（`playSelfPlay` の既定）は変更しない。** 引き続き、合法手すべてをランダムに引く（ADR-0005）。選ばせない手を作ると、その手が通る道筋がテストされなくなる。
- **対戦相手の CPU は、別の口として作る。** engine の `ActionPicker` は、盤面を受け取らないいまの形のままにする。CPU には、射影の盤面を受け取って手を選ぶ口と、射影の盤面と選択を受け取って答える口を、別に用意する。
- **対戦の部屋で打つ時も、CPU 同士の勝率を測る時も、同じ口を通す。** 通り道が分かれると、片方だけで起きる違いが生まれる（ADR-0017）。

### 1 手にかけてよい時間は、探索を始める時に決める

- CPU は、いまどおり部屋の決まりごとの中で同期的に打つ（`room.ts` の `withCpu`）。段階 1〜3 は、それで足りる速さに収める。
- **探索に時間をかける段階（5）に入る時に、1 局の対戦にかかる時間を測ってから、探索をサーバの外の流れ（`worker_threads` など）に出すかを決める。** 同期的に探索すると、その間サーバ全体が止まる。

## 検討した選択肢

- **盤面（`DuelState`）をそのまま渡し、見えない部分を読まないことを実装で守る。** 先読みが本物の盤面から始まるので、作りは簡単である。しかし、読んでいないことを型で確かめられず、強くなった理由がズルなのか区別できない。採用しない。
- **相手のデッキリストを知っている前提で推定する。** 推定が当たりやすくなり、強くなる。しかし、人は対戦相手のデッキリストを知らずに打つので、人と同じ条件ではない。採用しない。
- **engine の `ActionPicker` を、盤面を受け取る形に広げる。** 検証用の自己対戦と CPU が同じ口を使える。しかし、engine が CPU のための形を持つことになり、検証用の自己対戦の口に盤面を渡すと、見えない情報を渡さない決まりが口の側では守れない。採用しない。
- **初めから決定化モンテカルロ木探索を作る。** 最終的にはいちばん強くなりうる。しかし、遊び（プレイアウト）を打つ方策と評価関数が無いと質が出ず、強さを測る仕組みも無いまま作ることになる。段階を踏む。

## 既存の決定との関係

- **ADR-0005。** 検証用のランダム自己対戦の役割は変えない。対戦相手の CPU は、その流用をやめて別に作る。
- **ADR-0017。** CPU は部屋に座る参加者で、人と同じ道筋で打つ、という決定はそのまま。選ばない手を候補から外す、いまの決まり（`cpuCandidates`）は、段階 2 の点数付けに置き換わる。
- **ADR-0004・ADR-0010。** 射影の盤面は、画面に送るものと同じ。CPU が受け取る情報は、人の画面が受け取る情報と一致する。
- **ADR-0018。** 記録に残すのは行動と答えの並びで、CPU が選んだ手もその中に入る。CPU がどう選んだかは記録に要らないので、CPU を強くしても、記録済みの対戦を打ち直した結果は変化しない。

## 影響

- `server` の CPU が、盤面の代わりに射影の盤面を受け取るようになる。部屋の決まりごとは、CPU に渡す前に射影する。
- CPU 同士の勝率を測る仕組みができる。CPU を変える変更は、その勝率で確かめてから入れる。
- 仮の盤面を作る段階（3 以降）では、射影の盤面から盤面を作り直す仕組みが要る。

## 実装

- 置き場: 新しいパッケージ `packages/cpu`（`@revolution/cpu`）。engine にだけ依存する。`server` はこれに依存する
- CPU の型: `CpuPlayer`。手を選ぶメソッドが `pickAction(view: ActionView, random)`、選択に答えるメソッドが `answer(view: ChoiceView, random)`
- CPU が受け取るもの: `ActionView`（射影の盤面・行える行動・放棄したら何が起きるか）と `ChoiceView`（その選択が起きている盤面の射影・選択）。完全な盤面から作成するのは `actionViewOf`・`choiceViewOf` だけ
- いまの CPU: `randomCpu`。部屋で打たせる CPU は `server` の `cpu.ts` の `ROOM_CPU`
- CPU 同士の勝率を測る関数: 1 回のデュエルが `playCpuDuel`、比べるのが `compareCpus`。手元で動かすコマンドは `pnpm cpu-compare`（`tools/cpu-compare.mjs`）。名前で選べる CPU は `CPU_PLAYERS`
- 勝ち越したかの判定: `verdictOf`（基準は ADR-0061）

# ゲームの外の事情を条件にする行は、カードごとに扱いを決め、運用の注記で知らせる

カードのテキストには、ゲームの外の事情を条件にする行がある。対戦の外でのやり取りを条件に勝敗を決める行や、相手プレイヤー本人の属性を条件にする行である。総合ルールとフロアルール第2部には、こうした条件の確かめ方を定めた条が見つからない。engine は盤面しか知らず、条件を確かめる手立てを持たない。

この文書は設計として先に書く。実装はこの後に行う。コード上の名前は実装の時に決める。

## 呼び名

**運用の注記** — カードに印刷されていない、このサービスでの扱いを知らせる行。印刷されたテキスト（`card.ts` の `WrittenCard.text`）とは別の欄で持つ。

## 決めたこと

- **ゲームの外の事情を条件にする行の扱いは、カードごとに開発者が決める。** 一律の規則（常に満たさない、など）は置かない。条件の中身によって、ふさわしい扱いが違うためである。扱いは、次のどちらかにする。
  - **効果を持たない行として扱う。** その行は、能力として持たせない。誘発型能力の形の行でも、誘発させない。誘発して何もしない形にしないのは、バンクに入ると、優先権のやり取りと画面の表示が 1 回増えるためである。
  - **条件を、常に満たすものとして扱う。** その行は、条件の無い行として動く。
- **利用者に、ゲームの外の事実を尋ねない。** 相手に事実を申告させる選択は、作らない。答えないことも、偽ることも防げず、利用者本人の属性を、対戦の入力にすることになる。
- **効果で勝敗を決める命令は、足さない。** 勝敗は、敗北の条件を満たしたプレイヤーが敗北する形だけである（総合ルール 第3部 第3章）。
- **カードに、運用の注記の欄を足す。** 印刷されたテキストと違う扱いをしている行があるカードは、その旨を、運用の注記として持つ。通信の表記に載せ、カードの詳細の表示で、印刷されたテキストと見分けられる形で出す。デッキを組む時にも、対戦中にも、相手のカードを見た時にも、同じ場所で読める。開発者が決めた形である。
- **印刷されたテキストの欄は、原本のままにする。** 注記を、テキストの行に書き足さない。テキストは、カードに印刷されている表記である（総合ルール 第2部 第2章 2）。
- **注記の文面と、カードごとの扱いの理由は、カードの定義の側に置く。** engine は、注記の中身を読まない。

## 検討した選択肢

**一律に、条件を満たさないものとして扱う** — 方針が 1 つで済む。しかし、実際の卓では満たされうる条件まで、効果の無い行になる。

**相手に尋ねる** — 字面にいちばん近い。しかし、上に書いた理由で採らない。engine に、事実を申告させる選択と、効果で勝敗を決める命令が要り、CPU と、ランダムに手を選ぶ自己対戦（ADR-0005）にも、特別扱いが要る。

**そのカードを実装しない** — 読みを作らずに済む。しかし、ほかの行だけで使えるカードが、デッキに入れられなくなる。

**注記を、印刷されたテキストの行に書き足す** — 欄を足さずに済む。しかし、テキストが印刷のとおりでなくなり、原本との突き合わせで、毎回食い違いとして出る。

**注記を、発動した時のログにだけ出す** — 起きた瞬間に理由が分かる。しかし、効果を持たない行は、ログを出す機会が無く、デッキを組む時にも見えない。

## この決定が決めていないこと

- **運用の注記を、ほかの用途にも使うか。** 原本の字面から離れた読みをしているカードは、ほかにもある。それらに注記を出すかは、カードごとに決める。実装できるものを省いたことの告知に使うかも、決めていない。
- **注記の見た目。** 実装の時に、カードの詳細の表示を決めている ADR に書き、モックも直す（ADR-0032）。

## 影響

- **カードの表記に、欄が 1 つ増える。** engine のカードの定義、通信の表記、画面のカードの詳細、モックが変わる。古い画面は、注記を出さないだけで、落ちない（項目が増えるだけのため）。
- **この決定で書けるようになる形（BR1.0 の番号）。** 対戦の外でのやり取りを条件に勝敗を決める行を持つユニット（04。その行は、効果を持たない行として扱う）。相手プレイヤー本人の属性を条件にする行を持つユニット（21。条件を、常に満たすものとして扱う）。どちらも、運用の注記を出す。

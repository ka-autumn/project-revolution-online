# project-revolution-online

トレーディングカードゲーム「プロジェクトレヴォリューション」を、ルールを完全に自動適用する形で
オンライン対戦できるようにするプロジェクト。

ルールの拠り所は総合ルール Version 15.00 で、全文が [`docs/rules/`](docs/rules/) にある。総合ルールが
「詳細はフロアルールをご参照ください」と外へ投げたところは、フロアルール（Version 1.12）の第2部で、
こちらは [`docs/floor-rules/`](docs/floor-rules/) にある。
用語の正は [`CONTEXT.md`](CONTEXT.md)、設計上の決定は [`docs/adr/`](docs/adr/)。

## 構成

pnpm ワークスペースのモノレポ。

| パッケージ | 役割 |
| --- | --- |
| `packages/engine` | ルールエンジン。「盤面 ＋ 行動 → 次の盤面」の純粋関数。実行時依存を持たず、ブラウザとサーバの両方で動く（ADR-0001） |
| `packages/server` | 盤面の唯一の権威（ADR-0004） |
| `packages/client` | 対戦画面。受け取った盤面を描いて選んだものを送るだけで、ルールの判断は持たない（ADR-0010） |
| `private/cards` | カード実装。この公開リポジトリには含まれない（ADR-0002） |
| `private/decks` | 対戦に使うカードのまとまりを渡すだけ。カードを名指しするため、cards と同じく含まれない |

`private/` は**公開リポジトリに含められないパッケージの置き場**で、独立した非公開リポジトリを
そこへ clone する（ADR-0002）。作業ツリー上はワークスペースの一部として振る舞うが、コミット先が
別になる。

依存の向きは cards → engine の一方向で、engine は cards を知らない。**カードを名指しするのは
`private/decks` だけ**で、デッキの組み方もサーバの立て方も公開側にある（ADR-0002）。

## 開発

Node.js 22 以上。pnpm は `packageManager` で固定しているため、corepack が有効なら追加の準備は要らない。

```sh
pnpm install --frozen-lockfile
pnpm verify
```

`--frozen-lockfile` を付けるのは、`pnpm-lock.yaml` が `private/` 以下の importer を持っているため。
それらが無い環境で素の `pnpm install` を走らせると、ロックファイルから黙って消える。

## 対戦する

サーバと対戦画面を別々に立てる。

```sh
pnpm serve --decks private/decks/src/index.ts   # 対戦サーバ（既定で 8787 番）
pnpm --filter @revolution/client dev            # 対戦画面（既定で 5173 番）
```

**打った対戦は残る**（ADR-0018）。既定では立てたところに `revolution.sqlite` ができ、**サーバを
落として立て直しても、打っていた対戦はそこから戻る。** 残すのは盤面ではなく、デッキとシードと
「行動と答えの並び」だけである。置き先は `--store` で変えられ、空文字を渡せば何も残さずに立つ。

```sh
pnpm serve --decks private/decks/src/index.ts --store ''   # 何も残さない
```

`--decks` に渡すのは、次の 3 つを export するモジュールである（ADR-0021）。
**このリポジトリはどのカードを使うかを知らない**（ADR-0002）ので、実行時に受け取る。

| export | 何を渡すか |
| --- | --- |
| `pool` | 識別子で引けるカードのまとまり。ここに入っているものが、席に持ち込める全部である |
| `presets` | 誰でも使える既製デッキ。`{ id, name, cards }` で、`cards` は識別子の並び |
| `restrictions` | 名前の付いた禁止／制限リスト。`{ id, name, limits }` で、`limits` はカード名ごとの上限（同名のカードを合わせて数える）。空でよい。先頭のものが部屋の既定になる |

識別子は公開側にとってただの文字列で、何を指すかも知らない。デッキは識別子の並びなので、
何をどの枚数入れるかは渡す側が決める。積み方の取り決めはこのリポジトリに無い。立てる時に既製
デッキが構築戦の規定（総合ルール 第3部 第1章 3-1）を満たしているかを確かめるので、満たして
いなければその場で分かる。

**席に着く時に選ぶのは自分のデッキである**（ADR-0021）。既製デッキはコピーして自分のデッキに
してから使うもので、選択肢には並ばない。**ただしデッキを持てるのはログインした人だけ**なので、
上のようにログイン無しで立てた場合は、渡された既製デッキがそのまま選択肢になる。手元で 2 人ぶん
試すときは、席ごとに別の既製デッキを選べる。

あとは `http://localhost:5173` を開くだけでよい。**開くとロビーが出る**（ADR-0017）ので、
そこで部屋を作るか、開いている部屋に入る。

| ロビーで選ぶもの | 何が起きるか |
| --- | --- |
| 人と対戦する | 部屋を作って相手を待つ。作った部屋は、ほかの人のロビーにも出る |
| CPU と対戦する | もう一方の席にサーバが座り、そのまま始まる（ADR-0005 のランダムな手。強くない） |
| 入る | 相手を待っている部屋に入る。2 人揃ったところで始まる |

名乗りは画面が用意してブラウザに覚えさせる（ADR-0017）ので、**閉じても開き直せば同じ席に戻れる。**
そのぶん同じブラウザで開いた 2 つのタブは同じ人になるので、**手元で 2 人ぶん試すときは名乗りを
`?participant=` で分けるか、別のブラウザで開く。**

合言葉を決めて待ち合わせることもできる。URL に付けると、ロビーを通らずその部屋に入る。

```
http://localhost:5173/?participant=あ&room=あいことば
http://localhost:5173/?participant=い&room=あいことば
```

名乗り（`participant`）は認証ではない（ADR-0009）。これを知っている人がその席に座れるので、
切れても同じ名乗りで開き直せば続きから打てる。

**これは手元で立てたときの形である。** ログインを持たせると名乗りは受け付けなくなり、席は
Cookie のセッションで決まる（ADR-0019、「ログインできるようにする」）。

立てるにはカードの実装が要る。無い場合は下を参照。

## デプロイ

画面は Vercel で配信し、対戦サーバは常駐する 1 台のマシンに置く（ADR-0013、ADR-0014、
ADR-0015）。両者は同じオリジンである必要はなく、接続先は画面側が保持している。

### 対戦サーバのデプロイ

カードはデプロイ先でビルドさせない（ADR-0002）。ビルドは手元だけで行い、デプロイ先には
出来上がった 1 ファイルだけを渡す。

```sh
pnpm build:server --decks private/decks/src/index.ts    # dist/serve.cjs を書き出すだけ
```

デプロイまでまとめて行うにはこちら。**ビルド → 転送 → 差し替えて再起動**を順に行い、途中で
失敗すればそこで止まる。

```sh
pnpm deploy:server --decks private/decks/src/index.ts --host <ユーザ>@<ホスト> --key <秘密鍵>
```

デプロイ先は引数か環境変数で渡す。**このリポジトリはデプロイ先の情報を持たない。**

| 環境変数 | 意味 |
| --- | --- |
| `REVOLUTION_DEPLOY_HOST` | デプロイ先（`<ユーザ>@<ホスト>`） |
| `REVOLUTION_DEPLOY_KEY` | 使用する秘密鍵 |
| `REVOLUTION_DEPLOY_PATH` | デプロイ先でのパス |
| `REVOLUTION_DEPLOY_UNIT` | デプロイ先の常駐単位（systemd サービス）の名前 |

デプロイ先に何を用意するかは ADR-0015 を参照。**待ち受けポートは `PORT`、対戦の記録先は
`STORE` で指定できる**ため、どちらもビルドし直さずに変更できる。

### 検証環境へのデプロイ

ログインを含む画面変更を、本番より前に一通り確認するための常設の検証環境がある
（ADR-0025）。デプロイ方法は同じだが、コマンドと環境変数を分けている。

```sh
pnpm deploy:server:verify --decks private/decks/src/index.ts --host <ユーザ>@<ホスト> --key <秘密鍵>
```

| 環境変数 | 意味 |
| --- | --- |
| `REVOLUTION_DEPLOY_HOST_VERIFY` | デプロイ先（`<ユーザ>@<ホスト>`） |
| `REVOLUTION_DEPLOY_KEY_VERIFY` | 使用する秘密鍵 |
| `REVOLUTION_DEPLOY_PATH_VERIFY` | デプロイ先でのパス |
| `REVOLUTION_DEPLOY_UNIT_VERIFY` | デプロイ先の常駐単位の名前 |

**本番用の環境変数（`REVOLUTION_DEPLOY_HOST` など、末尾に `_VERIFY` が付かないもの）とは
名前が異なる**ため、片方だけを設定していても、もう一方のコマンドには読み込まれない。引数を
省略しても意図しないデプロイ先に届くことはなく、`pnpm deploy:server` と
`pnpm deploy:server:verify` は常に別々の宛先を向く。

**デプロイ先には絶対パスで `STORE` を指定すること**（ADR-0018）。既定値の `revolution.sqlite`
は相対パスのため、常駐単位の作業ディレクトリを基準に解決される。指定しなければ `/` が基準に
なり、意図しない場所に作成されてしまう。`/run` や `PrivateTmp` 配下も再起動時に消えるため避ける。

保存先ディレクトリは常駐単位自身に用意させるのが自然である。`StateDirectory` はその単位の
実行ユーザーの所有物として作成され（ADR-0015 の「専用ユーザーで実行する」という方針と
合致する）、再起動しても残る。

```ini
[Service]
StateDirectory=revolution
Environment=STORE=/var/lib/revolution/revolution.sqlite
```

**バックアップは別の場所に取り、取得できていることを確認する仕組みも用意する。** 送信し続けて
いるつもりでも失敗している場合、次に使おうとしたときに初めて気づくことになる（ADR-0015）。

### 検証環境への一括デプロイ

確かめるたびの作業（サーバを運ぶことと画面の alias を張ること）を1つにまとめたコマンドがある。
画面は Vercel の GitHub 連携が preview を作り終えるまで待ってから alias を張る。

```sh
pnpm publish:verify --decks private/decks/src/index.ts
```

サーバ側の引数・環境変数は `deploy:server:verify` と共通。画面側の張り先は追加で1つ要る。

| 環境変数 | 意味 |
| --- | --- |
| `REVOLUTION_VERIFY_CLIENT_DOMAIN` | 検証環境の画面が受け持つドメイン（alias の張り先） |

**PR の作成・更新のたびに自動では走らせない**（ADR-0025）。検証環境は常設1組しか無く、
「今どのブランチで確かめたいか」を手で選ぶ操作として残してある。

なお `deploy:server` が差し替えるのはビルド済みの 1 ファイルのみで、同じ場所に置いた他の
ファイルは削除されない。**とはいえ同じ場所には置かないこと。** デプロイ方法が変わったときに
巻き込まれてしまう。

**初めてのデプロイ先には、事前に鍵を登録しておくこと。** `deploy:server` は途中で止まらない
よう `BatchMode` で接続するため、`known_hosts` に登録されていない宛先は
「Host key verification failed」で失敗する。

**登録されていないのは、宛先自体が無いときだけではない。** ホストは種類ごとに異なる鍵を
持っており、`known_hosts` に載るのは接続時に選ばれた **1 種類だけ**である。別のクライアント
（Windows 標準の OpenSSH と Git 付属のものなど）が異なる種類を選ぶと、同じ宛先でも照合できない。
ホスト名と IP アドレスも別の宛先として扱われる。**種類ごとにまとめて登録しておくと確実である。**

```sh
ssh-keyscan <ホスト> | ssh-keygen -lf -    # フィンガープリントを確認する
ssh-keyscan <ホスト> >> ~/.ssh/known_hosts # 確認してから登録する
```

### 対戦画面のデプロイ

`vercel.json` にビルド方法が書いてある。設定が必要な環境変数は 2 つで、どちらも省略できる。

| 環境変数 | 意味 |
| --- | --- |
| `VITE_SERVER_URL` | 接続先サーバ（`wss://<サーバ>`）。**ビルド時に埋め込まれる。** 省略時は同一ホストの 8787 番ポート |
| `BASIC_AUTH` | 画面にかける Basic 認証（`名前:合言葉`）。省略時は認証なし |

**`VITE_SERVER_URL` を変更しても、再デプロイするまでは反映されない。** デプロイした URL を
開けばロビーが表示されるので、共有するのはその URL だけでよい。ビルド時に埋め込んだ接続先とは
別のサーバに繋ぎたい場合は、`?server=` で上書きできる。

```
https://<画面>/
https://<画面>/?participant=あ&room=あいことば   # 合言葉で待ち合わせるとき
https://<画面>/recipe/<鍵>                        # 共有されたレシピを開くとき（ADR-0022）
https://<画面>/share/<鍵>                         # 共有 1 つの公開ページを開くとき（ADR-0022、#197）
```

**`/recipe/<鍵>` と `/share/<鍵>` はどちらも画面側のパスである**（ADR-0022）。`/recipe/<鍵>`
（レシピの画面、共有を全部並べる）を開けるのはログイン済みのユーザーのみだが、**`/share/<鍵>`
（共有 1 つの公開ページ）はログインしていなくても開ける。** `vercel.json` の `rewrite` は
このどちらのパスも `index.html` へフォールバックさせるための設定で、Vercel にデプロイした
場合のみ有効になる。**それ以外の静的ホスティング（S3、GitHub Pages など、URL のパスをそのまま
ファイルとして探すもの）を使う場合は、同様の SPA フォールバック設定をホスト側で追加する
必要がある。** 追加しないと、共有リンクを開いたユーザーには 404 が返る。`vite dev` で手元起動
する場合は、既定で SPA フォールバックが有効になっている。

**画面にかけた Basic 認証はサーバには適用されない。** ログインを有効にしていない場合、**固定の
ホスト名を知っている人は誰でも接続できてしまう**（ADR-0014）。これを閉じる方法は次の節で
説明する。

**`BASIC_AUTH` を設定した画面では、`/share/<鍵>` も Basic 認証の内側に入る。** `/share/<鍵>`
はログインしていなくても開けるように作ってあるが、それは対戦サーバ側の話であり、**画面そのもの
にかけた Basic 認証はパスを選ばない。** 共有リンクを誰でも開けるようにしたい場合は、その画面の
デプロイでは `BASIC_AUTH` を設定しないこと。

### ログインを有効にする

ユーザーの身元を Google から受け取り、席は Cookie のセッションで決定する（ADR-0019）。以下の
4 つの環境変数をサーバに渡すと、ログイン済みのユーザーのみが接続できるようになる。**渡さなければ
従来どおり `?participant=` で名乗って入室する。両方を同時に有効にすることはできず、一部だけ
渡すと起動に失敗する。**

| 環境変数 | 意味 |
| --- | --- |
| `GOOGLE_CLIENT_ID` | Google Cloud Console で作成した OAuth クライアントの ID |
| `GOOGLE_CLIENT_SECRET` | 同クライアントのシークレット。**リポジトリに書かず、ビルド済みファイルにも埋め込まない** |
| `SIGN_IN_CALLBACK` | Google に登録するコールバック URL。`https://<サーバ>/auth/google/callback` |
| `SIGN_IN_RETURN_TO` | 認証後にユーザーをリダイレクトする画面の URL |

`SIGN_IN_RETURN_TO` の出所（オリジン）は、`/share/<鍵>` への CORS の許可先にも使う
（ADR-0022、#197）。画面がその公開ページを `fetch` するのはこの URL の場所からだけである、
という前提を、ログインの戻り先とは別の設定を増やさずに使い回している。

`SIGN_IN_CALLBACK` に指定した文字列は、そのまま Cloud Console の「承認済みのリダイレクト
URI」に登録する。**要求するスコープは `openid` のみ**のため、同意画面でメールアドレスや氏名を
求めることはない。サーバが保持するのは Google 上の識別子とセッション、そして**本人が設定した
表示名**だけである。

**表示名は初回接続時に本人が決める**（ADR-0020）。初めて接続したユーザーはサーバから入力を
求められ、決定するまで部屋の作成にも入室にもできない。決定した名前はロビーと対戦相手の画面に
表示され、いつでも変更できる。**同じ名前のユーザーが複数存在してもよい**——席を決定しているのは
名前ではなく身元である。

**画面とサーバは同じ登録可能ドメインの配下に置くこと**（ADR-0019）。`app.example.com` と
`duel.example.com` のように登録可能ドメインが一致していれば、オリジンが異なっていてもブラウザ
は Cookie をハンドシェイクに含めて送信する。**異なるドメインだと Cookie が送信されないため、
ログイン自体は成功しても接続はできない。**

**ログインを有効にする場合は保存先（`STORE`）も必須である。** 身元とセッションの両方がそこに
保存される。

**ログインを有効にすると、サーバは同じポートで HTTP も受け付けるようになる**（ADR-0019）。
リバースプロキシの設定にも、WebSocket に加えて通常の HTTP 経路を追加する必要がある。

## 開発の確認

`pnpm verify` は次の 3 つを順に実行する。

```sh
pnpm typecheck       # 全パッケージの型検査
pnpm test            # vitest
pnpm verify:engine   # エンジンが依存ゼロで、ブラウザ／サーバ両方向けにビルドできることの確認
```

## この公開リポジトリだけを clone した場合

`private/` が無いため、対戦を動かすことはできない。`pnpm verify` は通る。
エンジンのテストは実カードではなく架空のテストカードで書くため、カード実装の有無に依存しない（ADR-0002）。
クライアントも同じで、テストは手で組み立てた盤面に対して書くため、カード実装を要らない（ADR-0010）。

この状態では `pnpm install --frozen-lockfile` を使うこと。上に書いたとおり、素の `pnpm install` は
`pnpm-lock.yaml` から非公開パッケージの importer を消し、身に覚えのない差分を残す。
